# Working on Amoris

Amoris is an agent-native 3D game engine: Rust host, TypeScript scripts on QuickJS-ng, wgpu
rendering (Metal/Vulkan natively, Direct3D 12 on Windows, WebGPU in the browser), a React web editor, MCP for agents.
Read [the charter](docs/charter.md) first: it fixes the stack, the architecture and what this round
must prove; its section 8 lists the open decisions. The game-side subsystems are
specified under [docs/spec/](docs/spec/README.md); their measured spikes are under
[docs/spikes/](docs/spikes/).

## Layout

The whole tree, crate by crate, is [architecture.md 3](docs/spec/architecture.md); the rules behind
it are charter 5.4.

- `crates/`: the Rust workspace, flat. `tools/crate-graph.toml` groups the crates and lists their
  allowed edges, which `cargo xtask check`'s `deps` step enforces; a new crate or edge changes it
  together with architecture.md 5 and the charter's 5.1 tables.
  - game (`amoris-sim`, `amoris-assets`, `amoris-persist`, `amoris-physics`, `amoris-interface`,
    `amoris-script`, `amoris-runtime`, `amoris-check`) and link (`amoris-link`): headless, built for
    `wasm32`; game crates never depend on wgpu, winit, tokio or rmcp.
  - presenter (`amoris-render`, `amoris-audio`, `amoris-viewport`): they read the world only
    through the render feed in `amoris-assets`. `amoris-render` also holds the GPU water kernels,
    which the app crates install behind `amoris-physics`'s service interface.
  - tool (`amoris-mcp`, `amoris-server`, `amoris-debug`): they reach the game through
    `amoris-link`, and the debugger also through the script host's debug hook.
  - app (`amoris-app`, the native `amoris`; `amoris-web`, the browser's game module): the entry
    points that link the runtime with the presenters.
  - `crates/engine_version.rs` computes the engine source hash, which every file under `crates/`
    that Git does not ignore enters.
- Shaders live next to the renderer code that uses them (the library's in
  `crates/amoris-render/shaders/`), as `.wgsl` files, never Rust strings.
- `sdk/`: the script SDK's toolchain (TypeScript 7, `cd sdk && bun install`), which `scripts.check`
  finds. The `amoris` module itself is `crates/amoris-script/src/prelude/amoris.ts` (its `.js` and
  `.d.ts` are generated by `tests/prelude.rs`); `scripts.types` writes a project's declarations into
  `<project>/.amoris/types/`. How games are written: [docs/sdk.md](docs/sdk.md).
- `editor/`: the React web editor (Vite, bun); [docs/spec/editor.md](docs/spec/editor.md) says how
  to run it against the mock host (`bun run dev:mock`) or the real one, and what it needs from the
  host. Its harnesses in `editor/tools/` run from `editor/`. `desktop/`: the Electron shell around
  it ([docs/spec/desktop.md](docs/spec/desktop.md)).
- `web/`: the browser pages. `web/viewport/pkg` is the committed build of `amoris-viewport`
  (`tools/build_viewport.sh`); `web/pkg` and `web/projects/` are built by `tools/build_web.sh` and
  ignored.
- `samples/`: one project per folder. The games and demos are `blockcraft`, `sailing`,
  `sailing-course`, `anim`, `town-walk` and the six water games with a README (`pool-party`,
  `river-falls`, `surf-beach`, `water-pool`, `water-storm`, `water-valley`).
  `tests/fixtures/`: projects only tests and checks read: the checks' negative controls, the SDK's
  type test, and `scenes/`, the scenes that tests, checks and measurement tools read (eight
  `water-*` scenes, `gi-room`, `pt-lab`). xtask runs every `samples/*/check.toml` and `tests/fixtures/**/check.toml`.
- `bench/`: benchmark workloads and comparison harnesses (`agent-dev/`, `physics/`, `rules/`,
  `web/threejs_cubes.html`).
- `tools/`: Python, shell and Node scripts by purpose ([tools/README.md](tools/README.md)):
  `render/`, `water/`, `host/`, `runtime/` and `site/`, with what xtask, CI or several groups use
  at the top (the check's inputs `crate-graph.toml`, `clippy-determinism.toml`, `lint-fixture/`,
  and `gpu_matrix.py`, `build_web.sh`, `machine_conditions.py`, `web_bench.mjs` and the like).
  Scripts run from the repository's root and find it from their own file. `tools/neural/` trains neural assets, `tools/eval/`
  runs agent evaluations, `tools/tests/` tests the tools, and `tools/vscode/` holds the VS Code
  attach configuration for the script debugger. `xtask/`: `cargo xtask` (check, gen, webcheck,
  export-web).
- `shared/`: the shared contract and benchmark prose; `shared/contract/rust` is `amoris-contract`.
  `third_party/`: the patched `rquickjs-sys` (QuickJS-ng with PR #1421 and P1 to P13).
- `docs/`: charter, specs, spikes, benchmark methods and result tables. `site/`: the Pages
  showcase and user docs ([site/AGENTS.md](site/AGENTS.md)).

### Samples

Games and demos live in the engine's `samples/` (owner, 2026-10-25; charter 5.4). `blockcraft` came
from `qiulinfan/amoris-samples`; its integration commit names the source commit.

- Each game is one self-contained folder with its own README; games do not share files, and a new
  game gets a new folder. `sailing`, `sailing-course`, `anim` and `town-walk` predate this rule and
  have no README yet.
- Games use only the `amoris` module and scene and project files (`project.toml`, `scene.json`,
  `perception.json` and their assets).
- An engine gap a game finds is fixed in the engine, natively and in its own commit, never worked
  around in the game.
- Generated files (scenes, meshes, textures, volume cells) are committed together with the generator
  that writes them, in the project's folder (`build_scene.py`, `samples/blockcraft/gen_world.py`,
  `samples/town-walk/bake_town_walk.py`). Regenerate them; never edit them by hand.
- Run output, captures and logs go to the ignored `out/`, never into `samples/`.
- Assets are original or compatibly licensed, with their licence and source beside them (as
  `samples/town-walk/licenses/` and `CREDITS.txt`); large third-party models stay ignored and are
  fetched or packaged locally (`samples/town-walk/models/third-party/`).

## Rules

1. A change that departs from the charter updates the charter first, with the reason.
2. Keep `main` runnable end to end: add capabilities on top of a verified baseline.
3. Code is organized by responsibility, with no file-length limit. Performance is measured and
   recorded (docs/bench/), never a pass condition.
4. Testing is light and targeted: run the tests of the crate you touch; run the workspace before a
   commit that touches shared code. Research, reach and performance come first.
5. Material brought from another repository (third-party code; earlier, the now-retired Amoris
   Pioneer and amoris-samples) names its source repository and commit in the commit message, as
   `Source-repository:` and `Source-commit:` trailers.
6. Owner-facing explanations are Chinese; code, identifiers, commit messages and specs are English.
   The charter is Chinese.
7. Markdown under `docs/` is hard-wrapped at 100 display columns (CJK characters count two).
   Use `python tools/wrap_docs.py <file>`; recorded evidence remains unchanged.
   `shared/` changes with its contract record.

## Verification records and run archives

Do not track file checksums, audit manifests or file-digest provenance in Git. Local verification
may compute hashes in ignored `out/` storage. Keep source URLs, licenses and Git commit references.
Dependency locks and runtime content addressing, cache identities and deterministic state hashes
remain supported.

The engine tracks test code, fixed inputs, expected outputs, benchmark methods and concise result
tables. Raw measurements, logs, traces and run reports stay in ignored `out/` or CI artifacts.
Public archives belong in
[amoris-benchmarks-results](https://github.com/qiulinfan/amoris-benchmarks-results) after privacy and
credential cleanup. File-verification records remain local, including in that archive workflow.

## Building

- Rust 1.98.1 (`rust-toolchain.toml`); `source ~/.cargo/env` if cargo is not on PATH.
- A commit from before the 2026-10-16 rename is built from its exported tree after
  `python tools/amoris_rename.py --tree <dir>`, so this checkout's package names and `AMORIS_*`
  variables apply to it; `tools/runtime/qjs_bench.py build --rev` and `tools/runtime/publish_bench.py
  --build-base` do this themselves. Cargo then sorts the tree's lock again, so such a build goes
  without `--locked`; a page that loads the tree's own `web/viewport/pkg` needs
  `tools/build_viewport.sh` there first (`--tree` prints both). A build made before the rename, as
  the binaries saved under `out/`, ignores the `AMORIS_*` variables that every tool running another
  build sets (`--before`, `--build NAME=DIR`, `--exe`, `--amoris LABEL=PATH`) and refuses the
  renamed scenes: a re-run builds it again this way.
- `cargo build --release` builds the workspace; `cargo xtask check` runs the full local check.
  Its `gpus` step (after `test`, left out by `--quick`; owner, 2026-10-16) runs `amoris-render`'s
  GPU tests on every GPU adapter and native backend of the machine, `auto` on the adapters but the
  default one (`test` runs that one; `--only gpus` adds it) and the WebGPU baseline device, through
  `python tools/gpu_matrix.py --configs machine --workspace` (docs/bench/gpu-matrix.md 11): a test or
  test binary that failed, hung or found no GPU fails it, each skipped test is a warning (a skip is
  never a pass), and with no Python or no hardware adapter the step is skipped with the reason.
  `--only gpus` reruns it (about 10 minutes of both GPUs on R1); the per-binary logs are in
  `out/check/gpus/`.
- `wasm32-unknown-unknown` builds of QuickJS-ng need a clang with the wasm backend: the build script
  finds Homebrew's LLVM (`brew install llvm lld wasi-libc`) or `AMORIS_LLVM`. The viewport's
  meshoptimizer (levels of detail, [docs/spec/lod.md](docs/spec/lod.md)) needs it too, through
  `CC_wasm32_unknown_unknown` and, on Windows, `llvm-ar` on PATH: `cargo xtask` and
  `tools/build_viewport.sh` set both.
- `cargo xtask` discovers the same explicit LLVM override, pinned toolchain, then Homebrew LLVM.
  Its browser check needs Python with `websocket-client`; `AMORIS_PYTHON` selects that interpreter.
  GPU readback state locks must be released before `map_async`: wgpu can invoke a refused map's
  callback synchronously. Native Metal gives a process 32 timestamp query sets across all its
  devices and loses the device that creates a 33rd (`DeviceError::Unexpected`), so a renderer's
  profiler holds one (profiler.rs `QUERIES`) and parallel GPU test cases stay under the limit. The
  TAA image tests run in parallel, reject validation errors and unexpected device loss, and retain
  strict pixel comparisons. Local integration decisions and validation are in
  [pioneer-2026-10-16.md](docs/imports/pioneer-2026-10-16.md).
- Vulkan on macOS runs through MoltenVK (`brew install molten-vk vulkan-loader`); select it with
  `AMORIS_BACKEND=vulkan` and launch with `DYLD_FALLBACK_LIBRARY_PATH=/opt/homebrew/lib` so the
  loader is found. Metal is the default on macOS. `MVK_CONFIG_LOG_LEVEL=3` prints MoltenVK's shader
  compile errors; `cargo run --release -p amoris-render --example gpu_probe` checks a backend.
- Direct3D 12 is the Windows default (owner, 2026-10-09; `AMORIS_BACKEND=vulkan` picks Vulkan,
  `AMORIS_BACKEND=dx12` names D3D12 explicitly on any Windows run). A host (`amoris play`, `amoris
  serve`'s frames and GPU water, the renderer's window, the examples that draw or step water) with
  no backend named and no supported DXC runs Vulkan instead, D3D12 with FXC only when the machine
  has no Vulkan adapter either (owner, 2026-10-24; `amoris_render::host_backend`, outside the
  water's kernel key); amoris-render's tests keep `BackendChoice::from_env`, whose `Auto` is D3D12,
  while amoris-app's GPU water tests reach the water service through `src/water_compute.rs` and so
  follow `host_backend` (`AMORIS_BACKEND=dx12` or `AMORIS_DXC=fxc` tests D3D12 with FXC). DXC comes
  from the newest Windows SDK whose `bin\<version>\x64\dxcompiler.dll` is DXC 1.8.2502 or newer,
  wgpu's minimum (or `AMORIS_DXC`; `AMORIS_DXC=fxc` for FXC; an older DXC loses the device, so it is
  passed over for FXC); never enable wgpu's `static-dxc` (it downloads binaries). With no SDK DXC
  found (a player's machine without the SDK) and on Windows other than x86-64, D3D12 would compile
  with FXC. FXC does not run GPU water (owner, 2026-10-23; docs/bench/gpu-matrix.md 14): it cannot
  compile the generated kernels' `boundary_predict` (X3500) or `fs_shallow` (X3511), the fragment
  stage of every water region's surface, bound for every region every frame, whose invalid pipeline
  voids the submit: under FXC no frame of a scene with a water region draws, in view or not,
  CPU-solved or GPU, while scenes without water draw (R1, 2026-10-24). Water checks on D3D12 need
  DXC 1.8.2502 or newer. `AMORIS_ADAPTER=780m` (or an index) picks an adapter on a two-GPU machine,
  for any backend. D3D12 needs wgpu's indirect validation for `first_instance` (gpu.rs sets it);
  `cargo test -p amoris-render` checks it on Vulkan and D3D12
  (`indirect_draws_keep_their_first_instance`), `tools/render/backend_compare.py` compares frames across
  backends and `tools/render/backend_bench.py` times them ([docs/bench/dx12.md](docs/bench/dx12.md)). Debug
  builds compile the same optimized DXIL as release builds (`gpu::instance_flags`; the 780M
  mistraced the path tracer's unoptimized DXIL); `WGPU_DEBUG=1` brings unoptimized shaders with
  debug information back for PIX.
- `cargo xtask check`'s `test` step runs the GPU tests on the default adapter and backend; its
  `gpus` step (above) runs this machine's matrix.
  `tools/gpu_matrix.py --configs 5060-dx12,780m-vulkan,780m-auto,5060-dx12-minimal` (any
  `ADAPTER-BACKEND`; `auto` leaves `AMORIS_BACKEND` unset as xtask does) runs `amoris-render`'s
  tests once per adapter (`AMORIS_ADAPTER`), backend and the WebGPU-baseline device (`-minimal`)
  and prints a test-by-configuration table in which a test that skipped work for a missing
  capability shows as `skip`, and fails a configuration that found no GPU
  ([docs/bench/gpu-matrix.md](docs/bench/gpu-matrix.md)); build first (`--build-only`), run it
  under the bench lock on a shared machine, and run it after changing GPU paths that differ by
  vendor or backend. A test that leaves out part of its checks for a missing capability prints a
  line with the capability and `skipped` or `not checked`. Tests comparing backends run on every
  native backend, or on the one `AMORIS_BACKEND` names (`BackendChoice::under_test`, which names
  the others as not under test). Headless devices open one at a time (`Gpu::headless`): parallel
  Vulkan opens sometimes found no adapter.
- The renderer creates its pipelines on threads (`crates/amoris-render/src/par.rs`; in order in
  the browser): wgpu compiles shaders when a pipeline is created, DXC on every D3D12 start. wgpu's
  error scopes are per thread, so a pipeline error in `Renderer::new` reaches the device's
  uncaptured-error log, not a scope the caller pushed. Pipelines on the forward shader set its
  `SCENE_*` override constants from `SceneFormat::constants` (the motion and the view normal are
  computed only for a pipeline with their targets; the indirect share always, since NVIDIA's D3D12
  compiler rounds the color differently without it). `tools/render/build_compare.py` compares another
  build's frames with this one's, pixel for pixel. Release D3D12 builds discard wgpu's HAL labels;
  `WGPU_DISCARD_HAL_LABELS=0` brings the pass markers back for PIX. On the R1 laptop a start-up's
  all-core burst lowers the GPU's clocks for a few seconds: short headless benchmarks take
  `--settle 5` (many_cubes, splats, lod_field, `tools/render/backend_bench.py`; docs/bench/dx12.md 10).
- Per-frame profiling ([docs/bench/dx12.md](docs/bench/dx12.md), "Per-frame profiling"):
  `AMORIS_TRACE=frames=300,skip=60,out=PATH` (any renderer; `many_cubes --trace SPEC`) writes the
  render thread's CPU spans and every timestamped GPU pass of every frame as Chrome Trace Event
  JSON for ui.perfetto.dev or chrome://tracing, GPU time placed on the CPU timeline by a measured
  clock calibration (`crates/amoris-render/src/trace.rs`); `python tools/render/frame_trace.py stats
  TRACE` and `diff A B` give per-pass medians, p95 and spreads. Writing a trace holds the render
  thread 45 to 95 ms: a host that brackets frames (`trace_end_frame` says when the trace is
  complete) calls `finish_trace` outside its measured frames. RenderDoc (`RENDERDOC_DIR`, or
  scoop's `renderdoc`): `python tools/render/renderdoc_frame.py capture --backend dx12|vulkan --frame N
  --name NAME -- many_cubes --dense --bench 120` captures the renderer's N-th frame through the
  in-application API (`AMORIS_RENDERDOC_FRAME=N`; headless runs too) with RenderDoc's Vulkan layer
  loaded for that process only, and `analyze out/profiler/rdc/NAME.rdc` replays it in `qrenderdoc
  --python` (per-event GPU durations, the largest draw's shaders as DXIL or SPIR-V with their
  statistics and NVIDIA's Vulkan register count). RenderDoc's D3D12 counters need Windows'
  Developer Mode (`--d3d12-counters`); a first qrenderdoc start's analytics prompt blocks scripts
  until answered. Traces and captures stay under `out/profiler/`.
- Timestamp queries on Metal (also through MoltenVK) and on Vulkan with AMD adapters belong to a
  readback slot until sampling, deferred resolve and mapping finish
  (`profiler::deferred_timestamps`; charter, 2026-10-10 and its Pioneer note of 2026-10-15). A
  completion callback only marks the sampling submission ready; the render thread then batches
  resolves without waiting for the GPU. Never move their resolve into the sampling encoder: it can
  return another frame's counters, or zeros (the 780M on Vulkan, docs/bench/gpu-matrix.md 3 a).
  Clock calibration alone waits outside the measured window and dispatches real work. Run
  `frame_trace` and `gpu_profiler` integration tests on a deferred and an immediate backend after
  changing this lifecycle; see
  [docs/bench/metal-profiling.md](docs/bench/metal-profiling.md).
- The serve loop ([docs/bench/profiler.md](docs/bench/profiler.md) 6): the game thread snapshots
  through amoris-persist's `SnapshotCache`, which takes over a component section whose rows
  `bevy_ecs`'s change ticks say did not change, so a write to a persisted component must go
  through change detection (never `bypass_change_detection`, which clippy reports in the
  tick-code crates); a change there runs
  `cargo test -p amoris-persist --test repeated` and
  `cargo test -p amoris-runtime --features transpile --test snapshot_cache --test present`
  (`present` covers the extractor's kept queries; without the feature cargo refuses both).
  `/render` sends when the game thread publishes (`ThreadOptions::on_publish`), at most one frame
  every 8 ms (`cargo test --release -p amoris-app --bin amoris render_merges`).
  `tools/runtime/publish_bench.py` times the loop's work after a tick part by part (amoris-runtime's
  `publish_bench` example; `--build-base REV` compiles the same harness against an older runtime),
  `tools/host/serve_loop_bench.py` the live game thread with clients connected and the host's idle
  cycles, and `tools/host/gizmo_bench.py --dist` a drag against another editor build.
- AMD's Vulkan driver keeps compiled pipelines per executable in `%LOCALAPPDATA%\AMD\VkCache` and
  once kept a wrongly compiled one, served to every later run of one test binary path: a 780M
  Vulkan test that fails only there is rerun with `AMD_VK_PIPELINE_CACHE_PATH` at an empty directory
  before bisecting (do not delete `VkCache` without the owner's OK); `tools/gpu_matrix.py` gives
  each configuration's binary an empty one per run
  ([docs/bench/gpu-matrix.md](docs/bench/gpu-matrix.md) 9). The Vulkan SDK's validation layer is
  installed (scoop) but not registered with the system; `tools/render/vk_validate.py` enables it, with
  synchronization validation, for one command.
- Shader hashes are integer (`pcg_hash` in common.wgsl): `fract(sin(x) * k)` differs per vendor
  and API.
- Ray queries: the research tracers (`path_trace`, `gi_trace`, `ray_query_probe`;
  `crates/amoris-render/src/gi/`), the opt-in ray-traced sun shadows (`AMORIS_RT_SHADOWS=1`,
  [docs/spec/rt-shadows.md](docs/spec/rt-shadows.md)) and water reflections
  (`AMORIS_RT_REFLECTIONS=1`, water.md 67.4; instance masks keep each effect's rays to its own
  instances) need an adapter with wgpu's
  `EXPERIMENTAL_RAY_QUERY` (Metal; Vulkan and D3D12 on the RTX 5060 and the 780M here); their GPU
  tests run on every such backend and skip elsewhere. Keep ray queries local to the function that
  traces (naga 30 panics on a `ray_query` pointer argument) and test facing by triangle winding,
  not `candidate.front_face` (AMD's D3D12 driver miscompiles it). `python tools/render/rt_bench.py
  correctness|timing` compares the tracers with the M5 references (docs/bench/path-tracing-nrc.md);
  `python tools/render/rt_shadows_bench.py` measures ray-traced against cascaded shadows and regenerates
  their evidence (docs/bench/rt-shadows.md).
- Compute pipelines use `shaders::compute_options()` (no automatic workgroup zeroing: it breaks
  MoltenVK); a compute shader must initialize the workgroup memory it reads.
- Occlusion culling (two-phase Hi-Z, [docs/spec/occlusion.md](docs/spec/occlusion.md)) runs in
  `auto` mode by default; `AMORIS_OCCLUSION=off|on|auto` (the viewport page: `?occlusion=`) sets
  it. A change to culling or the opaque passes runs `cargo test -p amoris-render --test occlusion
  --test hiz` and `tools/render/occlusion_compare.py`: it must not change a single entity's coverage. A
  change to the pyramid or the late test also runs `tools/render/occlusion_mutations.py`.
- The depth prepass ([docs/spec/prepass.md](docs/spec/prepass.md)) runs in `auto` mode by default
  (GPU timestamps decide; off without them); `AMORIS_PREPASS=off|on|auto` (the viewport page:
  `?prepass=`) sets it. The forward and depth-only vertex stages must compute the clip position
  with the same expression, `@invariant`: a change to either, to the opaque passes or to the alpha
  test runs `cargo test -p amoris-render --test prepass` and the crate's `shaders` unit test, and
  `tools/render/prepass_compare.py` must not change an image. The auto mode's probes count only their
  own frames (each profiler reading names its frame): a change to them runs
  `cargo test -p amoris-render --lib prepass`, and `tools/render/prepass_bench.py --table <runs> --tails`
  shows the frames they draw the slower way and the frame time's tail.
- Shadow casters are culled per cascade by its box and its extruded camera slice
  ([docs/spec/occlusion.md](docs/spec/occlusion.md) 11; `AMORIS_SHADOW_CULL=off|on`, the viewport
  page's `?shadow_cull=`): a change to it, to the cascades or to `shadow_factor`'s offset, kernel
  or negative-depth guard runs `cargo test -p amoris-render --lib shadows`, `--test shadow_cull` on
  D3D12 and Vulkan, and the `shadow_cull` example's `compare`: no pixel may change.
- The render scale ([docs/spec/taa-gtao.md](docs/spec/taa-gtao.md) 4.1): `AMORIS_RENDER_SCALE`
  (0.25 to 1; the viewport page: `?scale=`) draws the opaque pass, prepass, Hi-Z and GTAO smaller
  and TAA upscales (the mode is promoted to TAA); `Targets::scene` is the opaque pass's size,
  `width`/`height` the output's. At 1 the frames must stay those of before: a change to the
  targets, the view uniforms (`texture_lod` scales every screen-derivative filter of the opaque
  pass) or taa.wgsl runs `cargo test -p amoris-render --test taa`, `tools/render/build_compare.py`
  against a build without it, and `tools/render/prepass_compare.py` with `AMORIS_RENDER_SCALE=0.5` and
  `AMORIS_AA=msaa+taa` (only the prepass's ties may differ: many_cubes' sphere, and walls touching
  a floor or ceiling); `aa_eval --only upscale` measures quality and `tools/render/aa_bench.py --scales`
  cost ([docs/bench/taau.md](docs/bench/taau.md)).
- Moving instances ([docs/bench/dynamic-scenes.md](docs/bench/dynamic-scenes.md)): `Scene::apply`
  must stay linear in the slots a tick moves (`cargo test -p amoris-render --lib scene::` pins it
  by structure and what each slot holds; `-- --ignored` times it); more than 8 runs of dirty slots
  are written as one buffer per binding-sized batch that a compute pass scatters (upload.rs, its
  GPU test `upload::`). `many_cubes --moving N [--sparse K]` moves cubes every frame and
  `python tools/render/dynamic_scenes_bench.py` times it (`--stall MS`: the idle-GPU control);
  `scene_changes` and `tools/render/build_compare.py` check the images.
- Transparency ([docs/spec/transparency.md](docs/spec/transparency.md)): instances whose material
  blends (glTF BLEND, a look's alpha below 1) or transmits (KHR_materials_transmission,
  `Model.transmission`) carry `FLAG_TRANSPARENT`; cull.wgsl keeps them out of the camera's list
  and `transparent.rs` sorts them on the CPU and draws them after the sky (`fs_transparent`), with
  GTAO on in a pass of their own after GTAO. A change to either, to GTAO's apply or to the opaque
  pass's attachments runs `cargo test -p amoris-render --test transparency --test draw_paths` and
  the library's `materials::`, `scene::` and `transparent::` tests;
  `python tools/render/transparency_pt.py` compares pt-lab with the path tracer by region and
  `python tools/render/transparency_bench.py` times the stage (docs/bench/transparency.md).
- The browser: `tools/build_viewport.sh` builds the WebGPU viewport into `web/viewport/pkg`
  (committed; the editor's `/wasm/` serves it), `tools/build_web.sh` also builds the game module
  into `web/pkg` and packs samples into `web/projects/` (both ignored). Serve `web/`
  (`python3 -m http.server -d web 8090`) and open `/?package=projects/samples-anim/package.json`.

## GPU water maintenance

The adopted scope (charter, 2026-10-25; docs/imports/pioneer-2026-10-25.md) is host-backed shallow
water with its frontier extensions and the played water games; dense 3D liquid stays out of scope
and thrown water is presentation only. WaterRegion selects cpu (default), gpu (full readback) or
gpu_resident. GPU errors stop and poison the tick; never substitute CPU work. Game-side crates never
link wgpu. Native hosts and the browser worker install the numerical service through
amoris-runtime::water_compute.

Resident water persists checked complete MAC checkpoints, bounded programs and GPU field digests.
After initialization CPU tiles are empty: never read them or omit checkpoint data when merging
feeds. Every replay step executes and checks the kernels' and program's identity (the deterministic
kernels compute the same bits on every device, water.md 66); no missing base, changed environment or
failed receipt may silently reset state. Publication uses exact-version section deltas. Resource
snapshot reuse follows ECS change detection just like components.

A suspended tick is not a boundary: do not publish it, repeat earlier systems/sources, or apply
queued commands until completion. Restore cancels old requests and clears derived observations.
GPU readback locks must be released before map_async; a refused map may callback synchronously.
The worker's external_ms is separate from active step_ms; add both and publication for complete
tick cost. Visual replica solve submissions are outside per-frame GPU pass totals.

Explicit probes, Walkers, Floater and Hull points share MAX_SAMPLES=4096 per region. Queries must
identify current positions, field owner/grid/checkpoint/digest, coupling mode and tick. Covered
dry fields mask Sea. Hull's three typed roles never borrow Floater indices. Consume observations
before Rapier integrates, and never relabel old values after pose, column, region or timeline
changes. Script observations are frozen; Update normally sees the preceding completed tick.
Sleeping Walker column data may rebind a new pose only if the column and complete field identity
are unchanged; active/edited/restored fields query again and consumption authenticates current pose.

WaterFeedback packets belong to the preceding completed boundary, apply before transport and clear
only after a checked result. Queue each newly applied horizontal force once. Supported-face
sampling and reaction distribution share a footprint, including rejected wall/dry shares; scalar
MAC writes must not race through a vec4 update. Budgets do not prove occupied volume, vertical
impact or global energy conservation. Never use old Sea readings as post-integration field data.

Changes run renderer water_compute/water_resident/water_summary/water_samples/water_reactions/
water_frontier, physics field_buoyancy/field_hull/resident_swimming/added_mass/vessel, runtime
water_resident_async/water_feedback, and app gpu_water/gpu_floaters/gpu_feedback/gpu_swimming/
gpu_energy/gpu_frontier_scenes/gpu_scale. A joined seam (water.md 64.3) is worked out once a tick,
in physics `join.rs`, from both regions' last edge columns, and both regions take the same numbers;
a joined group sleeps or bakes only as a whole. A `Terrain`'s heights come from its features through
`amoris_sim::math` (water.md 65); its collider is derived when its hash changes, never by change
detection, and the edit world shows resident regions as tiles until their first step. The renderer's
terrain pick marches the heights (`terrain.rs` `hit`); a change to either runs physics
`terrain`/`author`, render `terrain`, runtime `terrain`, app `gpu_authoring` and, in `editor/`, `bun
test` and `tools/water-authoring.ts`. The non-hydrostatic solve runs two identical Chebyshev cycles,
never one (water.md 55.2); its blocked dispatches must match one dispatch an iteration bit for bit
(water_frontier `the_blocked_non_hydrostatic_solve_matches_one_dispatch_an_iteration`). A change to
the kernel's velocity transport or its wet/dry faces also runs the `water_swash` example against the
table in water.md 61.3. The plunging lip's rules live twice, in water_compute.wgsl (`plunge_share`)
and in the renderer's water_lip.wgsl, which must stay the same (render tests water_lip and
water_frontier `plunging_crests_land_ahead_of_the_front_and_conserve_water`). Rebuild paired web
game/viewport and run actual Chrome worker/resident/probe/floater and water_pool_check.mjs checks.
samples/water-pool uses real player input and only scores poses/contact; scripts never move the
swimmer.

The water kernels the pipelines load are generated (water.md 66): render `tests/water_det.rs` makes
`shaders/det/` from the WGSL sources and `water_det.wgsl`, rounding every f32 operation once behind
a guard no compiler sees through and building division, roots and the transcendentals from such
operations, so every device computes the same bits; no pipeline loads a source kernel. After a
kernel or `water_det.wgsl` changes, `AMORIS_BLESS=1 cargo test -p amoris-render --test water_det`
rewrites them; a change of the numbers rewrites app `gpu_determinism`'s record (`AMORIS_BLESS=1`),
which then passes on Metal, Vulkan and `AMORIS_GPU_MINIMAL`, and in Chrome by
`tools/water/water_determinism_check.mjs`, also with `--adapter swiftshader`. Every value the CPU hands
the kernels goes through `field_f32`. A built-in new to the kernels needs its form in
`water_det.wgsl` and its CPU mirror in the probe (`the_kernels_arithmetic_is_the_cpus_bit_for_bit`).

Rendering uses actual GPU fields, preserves dry-region ocean ownership and WebGPU's eight fragment
storage-buffer limit. Test water image cases, water_foam and the actual browser after visual
changes. The wet bed (water.md 61.2) finds its points from this frame's scene depth, resolved
before it draws; check it from a moving camera (`shore_shots`), not only a still one. Keep
no-water behavior unchanged. Compute pipelines use shaders::compute_options();
initialize workgroup memory explicitly. Benchmark methods and measured scope are in
docs/bench/liquids.md; raw logs/traces stay under ignored out/. GPU interval sums/coverage are
not hardware utilization and can include stalls.

The water's sound (water.md 59) is presentation: a listening renderer's spray emitters tally each
kind's events and dissipated power, and amoris-audio's `water` rings bubbles from the tally. The
spray's compute stage holds eight storage buffers, WebGPU's per-stage limit. Changes run renderer
water_spray (also under AMORIS_GPU_MINIMAL) and amoris-audio's tests, and compare the `water_sound`
example's levels with liquids.md 10.

The wind sea (water.md 60) is presentation too: `Sea.fetch_km` and the first `Wind` raise it,
synthesized in three FFT cascades in four dispatches (ocean_waves.rs and .wgsl), drawn on the sea
and as the regions' detail; `Sea.look` and the regions' Sea sides join the two over a band.
Persisted types are written with PCE, which refuses a field left out by `skip_serializing_if`: a
new field of one has a default and bumps the type's version (`Sea` is version 2, its sailing chain
re-blessed).
Changes run the renderer's `ocean_waves` tests and water
`a_region_open_on_a_sea_with_its_look_meets_it_without_a_seam` (also on MoltenVK and under
AMORIS_GPU_MINIMAL), runtime water `a_seas_wind_sea_and_look_persist_and_reach_the_feed`,
`ocean_shots`' views and liquids.md 12's trace.

The wind and the rain on resident regions (water.md 67): `WaterPhysics.wind` adds the wind's stress
to every wet face in the kernels, its gusts by the deterministic sine; `WaterPhysics.rain` adds the
rain a whole millimetre at a time, what a region is owed kept in f64 in `WaterResident`, and the
ledger counts it. A region the wind blows on never rests; rain wakes it for each millimetre. Changes
run physics `weather`, app `gpu_weather` and `gpu_determinism` (`samples/water-storm` is in the
record), runtime water `the_weather_reaches_the_feed_and_the_rain_persists`, and, for the drawn
rain, the storm in Chrome. Traced reflections replace the forward shader's `water_reflect` by
rt_reflections.wgsl's; a change to either runs render `rt_reflections` and the library's
`rt_shadows` tests, and liquids.md 19's frame comparison.

The water must not shimmer (water.md 68): its refracted and reflected rays take the ripples and the
rain's rings averaged over four pixels, and the caustics' map follows its photons over 40 ms of
drawn time and stands still while drawn time does. A change to the water's shading, the ripples or
the caustics runs `tools/water/water_flicker.py` on the pool party's deck view against liquids.md 20
(the M5's figure at the current build).
