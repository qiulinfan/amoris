# Direct3D 12: backend choice and measured cost

Direct3D 12 is the Windows `Auto` backend by the owner's decision. Metal remains the macOS
backend and Vulkan the default elsewhere. The Windows comparison below records the trade-off;
it does not imply that one backend is fastest for every scene or GPU.

Design and API: [architecture](../spec/architecture.md), [charter](../charter.md),
[SDK](../sdk.md). Measurement conditions are summarized in
[quiet measurements](quiet-2026-10-09.md).

## Configuration and implementation

- `POCKET_BACKEND=dx12|vulkan|metal` selects a native backend. `POCKET_ADAPTER` accepts an adapter
  index or a case-insensitive name fragment, such as `nvidia` or `780m`.
- D3D12 uses a dynamic DXC from a Windows SDK, at least 1.8.2502, or the DLL/directory named by
  `POCKET_DXC`. `POCKET_DXC=fxc` selects FXC; an unsupported DXC is skipped. The build does not
  download a static DXC binary.
- D3D12 keeps wgpu indirect validation enabled. Indirect first-instance and base-vertex values
  must reach the shader correctly on every draw path.
- D3D12/Vulkan pipeline construction uses bounded native tasks. Browser construction is ordered;
  Amoris's Metal integration uses synchronous backend entry points. Native error handling must
  also collect uncaptured errors from pipeline-construction threads.
- Motion and normal outputs are computed only when their render targets exist. The indirect-light
  share remains computed to preserve the tested color rounding.
- Unchanged uniforms, bloom parameters and skinning jobs avoid repeated writes. Bloom and
  skinning bind groups remain cached until their buffers or targets change.
- Release D3D12 omits HAL pass labels. `WGPU_DISCARD_HAL_LABELS=0` restores markers for PIX;
  ordinary validation messages retain their labels.

## Machine and method

The final Windows measurements were taken on 2026-10-10, after the forward-shader and encoding
changes: ASUS ROG Zephyrus G14, Ryzen 9 270 (16 threads), 15 GiB, Windows 11 Pro 10.0.26200,
RTX 5060 Laptop 8 GB and Radeon 780M, on AC with Balanced power. Drivers: NVIDIA 617.14
(32.0.16.1714), AMD 32.0.13062.3005 / Vulkan 24.30.62.03; wgpu 30.0.1, DXC 1.8.2502.11.

The sphere and dense grid contain 1.6M cubes; the splat garden contains 1M splats. The crowd
workload adds 40 skinned columns. Configurations alternate within each round: five rounds
headless, three windowed. Headless runs wait five seconds after initialization; the NVIDIA GPU
starts each round at 70 C or below. Desktop background load remains a measurement limitation.

All configurations pin `POCKET_AA=msaa POCKET_GTAO=off POCKET_OCCLUSION=off`. These pins compare
backends rather than their adapter-dependent visual defaults. Headless examples use 1280x720;
windowed measurements use the presenting window's physical size (2560x1440 here).

- Frame: submit-to-idle p50 headless, presented-frame p50 windowed.
- GPU: mean of timestamped passes; this is different from frame wall time.
- CPU: encoding p50 headless, mean windowed.
- Cells: median of rounds, followed by minimum and spread `(max - min) / median`; all in ms.

## Interpretation and limits

On the RTX 5060, D3D12 costs 14% more GPU time for the dense headless grid and 44% more for the
windowed dense grid. Light headless scenes cost 2–16% more GPU time. The skinned crowd's frame
cost is 45% higher, and light-scene CPU encoding costs 1.6–2.3 times Vulkan's. The windowed
sphere is 10% faster with D3D12; windowed splats are close.

On the 780M, D3D12 is faster for the cube layouts and splat garden, but the crowd costs 9% more
GPU time and 19% more frame time. Treat these results as workload-specific, including the CPU
work of skinned parts, rather than as an unconditional integrated-GPU advantage.

D3D12 renderer construction takes about 0.18–0.21 s, still roughly 3–4 times Vulkan's median.
Device creation remains about 0.8 s longer. The Windows driver enumeration and lack of a D3D12
pipeline cache remain costs; FXC starts about 0.4 s slower than DXC in this final build.

The windowed dense-grid gap is unresolved. NVIDIA Vulkan initialization/opaque timings are
bimodal, reflected in the ranges and spreads above. Repeated timing and wall/GPU separation are
necessary before claiming small improvements. These Windows figures are not Apple measurements.

## Correctness and reproduction

The Windows implementation was checked on both GPUs with D3D12 and Vulkan, including minimal
features, forward variants, scene changes, Hi-Z, LOD, TAA, neural materials and ray-traced shadows.
The shader/encoding changes preserved all 72 deterministic before/after image pairs. Cross-API
images have small rounding differences; animated separate-process captures also have a time floor.
A source check does not replace fresh validation of a different platform or integration tree.

```sh
cargo build --release -p pocket-render --examples
POCKET_AA=msaa POCKET_GTAO=off POCKET_OCCLUSION=off python tools/backend_bench.py \
  --adapters nvidia,780m --variants vulkan,dx12 --rounds 5 --settle 5 --cool 70 \
  --cases cubes-sphere-headless,cubes-dense-headless,splats-headless,crowd-headless \
  --summary out/bench-runs/dx12.json
python tools/quiet_tables.py dx12 out/bench-runs/dx12.json
cargo test --release -p pocket-render --test scene_changes --test forward_variants
```

Windowed runs select the three `*-window` cases and three rounds. Keep detailed captures and
machine records in ignored `out/`; publish the method and aggregate results after review.

The [fixed historical
report](https://github.com/qiulinfan/amoris-benchmarks-results/tree/main/sources/pioneer-20261010/docs/evidence/quiet/dx12)

## Per-frame profiling (Pioneer, 2026-10-10)

Metal now uses completion-gated query resolves and an active calibration dispatch; see
[Metal profiling](metal-profiling.md). The Windows measurements below retain their original
method and results.

The dense-grid gap had no per-frame or per-draw view: the benchmarks above average the passes'
timestamps over a run. Three tools now give one.

- **Frame trace**: `POCKET_TRACE=frames=N[,skip=S][,out=PATH]` (any renderer, `pocket play`
  included) or `many_cubes --trace SPEC` records every frame's CPU spans on the render thread
  (asset polling, scene sync, uniforms, each pass's encoding, submit; the window's update, surface
  acquire and present; the headless wait for the GPU) and every timestamped GPU pass, per frame,
  as Chrome Trace Event JSON for ui.perfetto.dev or chrome://tracing
  (`crates/pocket-render/src/trace.rs`). Defaults: skip 60, record 300,
  `out/profiler/trace-<backend>.json`. While tracing, the post chain is timed as "post". Writing
  the trace holds the render thread once for 45 to 95 ms (the GPU drain, the end calibration, the
  export; logged): a benchmark writes it after its measured frames (the headless loop after it,
  the window when it closes), `pocket play` as soon as it is complete, one frame that long.
- **Statistics**: `python tools/frame_trace.py stats TRACE` gives per GPU pass and CPU span the
  median, p95, minimum, maximum and spread, the frame interval and its spikes, the GPU's busy time,
  frame span and idle gap before each frame, and the submit-to-GPU-start latency; `diff A B`
  compares two traces row by row.
- **RenderDoc**: `python tools/renderdoc_frame.py capture` records one frame under RenderDoc 1.46
  (`POCKET_RENDERDOC_FRAME=N`, the in-application API, so headless runs are captured too);
  `analyze` replays it in `qrenderdoc --python`: per-event GPU durations, the largest draw's shaders
  as DXIL or SPIR-V with instruction statistics, and on Vulkan NVIDIA's own pipeline statistics
  (registers, binary size).

**GPU time on the CPU timeline.** wgpu 30 exposes no clock calibration. On the Windows backends
measured here, before the first and after the last recorded frame the trace submits an empty
compute pass with timestamps to an idle GPU
eight times: its first timestamp lies between the CPU time before the submit and the CPU time the
wait for the GPU returned. The intersection of the brackets bounds the clocks' offset (13 to 86 us
in the runs below); GPU spans are placed with its midpoint, with drift interpolated when the start
and end calibrations disagree beyond their widths (about -10 ppm here).
`tests/frame_trace.rs` checks that each headless frame's GPU work lands between its submit and the
end of the wait that follows, and fails when the placement is off by 0.3 ms or the frames are
associated off by one; a unit test in `trace.rs` places passes under calibrations 100 us apart
and fails when the drift is interpolated the wrong way, not at all, or not linearly.

**Limits.** RenderDoc's D3D12 counters (per-event GPU duration) need Windows' Developer Mode, a
system setting this run did not change; without it the counter fetch loses the replay's device, so
`analyze` skips it on D3D12 (`--d3d12-counters` once enabled): per-event replay timings exist for
Vulkan only, and the in-engine trace gives D3D12's per pass. NVIDIA reports registers and binary
size only through Vulkan's pipeline executable properties; RenderDoc's NvPerf counters failed to
initialize. A first `qrenderdoc` start shows an analytics prompt that blocks scripts until it is
answered (this machine now has `Analytics_TotalOptOut` in RenderDoc's `UI.config`). The traces were
checked by `tests/frame_trace.rs` and `tools/frame_trace.py`, not opened in Perfetto's or Chrome's
viewer in this run. A command on a running host's catalog was not added: the catalog runs on the
game thread (`pocket-runtime`), which has no renderer; renderers live in `pocket play`'s window and
the browser viewport.

### Diagnosis (first)

- **The gap is the opaque pass's GPU time, and the pass is one draw.** Culling, post and the GPU's
  idle time are equal or smaller with D3D12; its CPU submit costs 0.25 ms more a frame, which a
  GPU-bound frame hides. In the rounds where both APIs ran at the same memory clock, D3D12's
  opaque pass is 20% dearer at 2560x1440 headless (one round) and 10% dearer in the window at
  1600x900 (two rounds), with an SM clock as high or higher. RenderDoc puts the whole pass in one
  sub-draw: per-draw attribution cannot split it further; the next level is inside the draw
  (shader, rasterization, depth).
- **Frame to frame.** Vulkan's frames are steady (p95 within 5 to 10% of the median). D3D12's are
  steady in the window, but the first headless D3D12 run had 19 frames over 1.5 times the median
  (up to 326 ms, the opaque pass itself), most likely outside load: the other two rounds had 0
  and 3. In the window both APIs are GPU-bound with no bubbles: the GPU idles 0.03 to 0.06 ms
  between frames, the CPU waits in the surface acquire for 94% of each frame, a frame's GPU work
  starts about one frame after its submit, and present takes 0.3 ms. Neither API shows pacing or
  present stalls on this display path.
- **Window against headless: open.** At 1600x900 Vulkan's opaque pass costs the same in the
  window and headless (20.00 and 19.83 ms, P2 throughout). D3D12's headless runs all held P4 and
  its window runs P2 but the first: the two at P2 were cheaper than the headless median (21.92
  and 22.02 against 23.68 ms), the one at P4 dearer (24.91). The ratio of the 1600x900 headless
  medians (1.19, against the window's 1.10) is confounded the same way, D3D12 at P4 against Vulkan
  at P2 in every round. Nor does the memory clock act alike: D3D12's window run at P4 was 13 to 14%
  slower than its runs at P2, Vulkan's 2560x1440 headless runs at P4 4 to 5% faster than its run
  at P2. This run cannot repeat the earlier +44% window gap either, measured through the laptop
  panel and the 780M (2560x1440): the display path changed.
- **The compiled shaders sample the same in the same loops.** The same interpolants reach both,
  and both sample six times (four with gradients, one at a level, one depth comparison) in 13
  loops. What differs: the DXIL has fewer conditional branches (57 against 66), keeps dynamically
  indexed copies of `view.cascade_splits` in local arrays (cold here: shadows are off), and reaches
  each of its samplers through wgpu's sampler-index indirection. NVIDIA reports 64 registers for
  the Vulkan shader; the D3D12 shader's register count and occupancy are unknown without Nsight
  or PIX.

### Next experiments

1. A trivial fragment shader (constant colour, same vertex shader and depth state) on both APIs: if
   the D3D12 premium stays, it is rasterization, depth or blending in the driver (Unreal's
   prepass-free control is 13% dearer on D3D12: branch `explore/ue5`, docs/bench/ue5-dense.md 6.3);
   if it goes, it is the shader.
2. A forward variant without the cold paths (shadows, probe GI) and with the cascade split
   selected without dynamic indexing: DXIL size and D3D12 time against Vulkan's.
3. Samplers: a forward variant that samples nothing (the environment from constants) to price
   the sampler-heap indirection on D3D12.
4. Pairs at the same memory P-state only, more rounds: they decide the window against headless on
   D3D12 and the 1600x900 headless ratio (the window case held P2 in five of six runs, D3D12's
   1600x900 headless runs P4 in all three); and the window case again on the laptop panel, where
   the +44% was measured.
5. Windows Developer Mode, for RenderDoc's D3D12 per-event timings, or Nsight Graphics (both the
   owner's decision): occupancy, register count and warp stalls of the D3D12 shader.
