## GPU 水本轮交付范围（2026-10-21）

所有者要求保留已验证的 GPU 水物理系统，并停止未完成的扩展。正式保留浅水求解、
GPU 常驻检查点和有限回放程序、稀疏查询、浮力/水平反冲、游泳交互，以及原生和浏览器
的真实游戏接入。冲浪小游戏、完整瀑布、三维自由液面和流体/刚体压力研究不纳入交付。

`WaterRegion.solver` 显式选择默认的 `cpu`、完整回读的 `gpu` 或 `gpu_resident`。
CPU 保持跨目标确定性；GPU 使用 WebGPU 基线支持的 f32，只在相同执行环境验证回放。
设备、内核或程序身份不符时拒绝执行；GPU 失败停止并毒化 tick，不切回 CPU。

游戏侧仍不链接 wgpu。物理拥有世界状态和计算接口，原生宿主与浏览器 worker 注入 GPU
服务。常驻状态由精确检查点、GPU 摘要和有界程序重建；每 tick 只回读所需观察与汇总，
初始化后不读取旧 CPU 瓦片。等待不是边界，不能重复系统、发布半个 tick 或执行排队命令。

渲染器直接消费相同检查点和程序，保留已验证的水场绘制、光学及泡沫等基础功能。
这些功能不代表海滩视觉质量、破浪或密集落水已完成。游泳样例用于验证输入、相机和
当前水场接触；排水体积、垂直冲击和完整双向能量耦合不在本轮完成范围。

当前契约和检查命令见 [water.md](spec/water.md)；保留范围见
[GPU 水集成状态](spikes/water-modernization.md)。

**Pioneer 2026-10-22（`explore/water`、`explore/water-nh`）。** 所有者要求在 Amoris Pioneer 上把水物
理继续做到前沿水准，并以三个游戏场景验收：河流汇入瀑布、泳池派对、强浪海滩冲浪。为此 Pioneer 越过上
文 2026-10-21 的交付范围，在 `gpu_resident` 区域上加入以下能力，契约见 [water.md](spec/water.md)
46–57，测量见 [liquids.md](bench/liquids.md) 7、8：

- 物体排水的竖直双向耦合：浮体点和游泳者把水面下的体积作为压力水头加到水柱上，水量严格守恒（思路来自
  M. Müller, GDC 2008）。浮力按步末位置线性隐式求值（D. Baraff 与 A. Witkin, SIGGRAPH 1998），阻力隐
  式。
- 瀑布：落差超过 `falls_m` 的面通量沿抛物线落到落点并带去水平动量，体积严格守恒（参照 N.
  Chentanez、M. Müller 与 T.-Y. Kim, IEEE TVCG 21(10), 2015）。
- 破浪：A. B. Kennedy 等（2000）的涡黏性模型。
- 色散表面波：S. Jeschke 与 C. Wojtan（ACM TOG 42(4), 2023）的浅水与 Airy 表面波分解，Airy 步用 J.
  Tessendorf（2014）eWave 的指数积分。色散区域的 `Sea` 边以 Airy 相速度送入任意水深上可解析的涌浪
  （波数用 J. D. Fenton 与 W. D. McKee 1990 的显式公式），所有者 2026-10-18“`Sea` 边须立在浅水中”的
  二十分之一规则和 `water.deep_edge` 对这类区域不再适用；不开色散的区域照旧。所有区域的 `Sea` 边线性
  强迫在破碎极限处截止：水面高出静水面的部分不超过水深的 0.4 倍，速度不超过长波波速的一半（J.
  McCowan, 1894）。
- 冲浪板和漂流圈（`Board`）与骑乘（`Walker.mount`），游泳者踩水，入水水冠，近镜头水花淡出，水下焦散
  （C. Wyman 与 S. Davis, I3D 2006；M. Shah、J. Konttinen 与 S. Pattanaik, IEEE TVCG 13(2), 2007）。
- 平静阻尼按区域设定：`WaterRegion.calm_per_s`。所有者 2026-10-18 定的 0.2/s 仍是默认值，没有设置它
  的场景行为不变；冲浪样例取 0，泳池取 0.05，因为 0.2/s 每秒会吃掉小波大约一成的波高。
- 非静水压：Y. Yamazaki、Z. Kowalik 与 K. F. Cheung（IJNMF 61(5), 2009）的深度积分非静水压模型，作为
  色散分解之外的第二种色散模型：弱色散、非线性，适合在海滩上浅化成浪的长涌浪，冲浪样例用它。离散压力
  力取离散连续性算子的转置，压力不做功；每个子步在静压动量更新与质量输运之间求解；Chebyshev 迭代（Y.
  Saad, 2003）做两个相同的循环，误差多项式平方后不再为负，求解再粗也不会让深水短波的重力反号。
- 附加质量与入水冲击：`Floater.added_mass` 是 J. R. Morison 等（1950）惯性项的附加质量系数，浮体点的
  力由物体与它带动的水共同承担；入水时按 T. von Kármán（NACA TN 321, 1929）的动量理论，把竖直相对速
  度交给新带上的水。
- 能量：浮体在同一步里感受到自己排开的水头。此前它晚一拍才感到，像一根滞后的弹簧，在无摩擦的封闭湖里
  把能量泵进湖水；现在浮体与湖水的总能量每 15 s 都在下降（`gpu_energy`），深水非静水压水池的能量（含
  竖向动能）5 s 后仍为初值的 1.0001。
- 亚网格交互涟漪（2026-10-22，任何求解器的区域都有，只做表现）：渲染器在离相机最近的水区域上开一个
  512×512 的细网格窗口，用 J. Tessendorf 的 eWave（2014）指数积分逐傅里叶模态精确推进线性毛细-重力
  波，四个水深层按水深混合，随流场平流，墙与干地反射、岸边吸收，场自身能承载的长波交还给场；浮体点、
  游泳者的身体、划水与趴板划水的手按相对水体的运动激发涟漪，焦散也透过涟漪折射。涟漪不进世界、快照、
  世界哈希与回放；没有搅动点的场景画面逐像素不变，`AMORIS_RIPPLES=off` 可关闭。

验收：`amoris-app` 的 `gpu_frontier_scenes` 用玩家的第一人称动作玩通
`samples/pool-party`、`samples/river-falls` 和 `samples/surf-beach`；三个样例导出的网页包在 Chrome
的 WebGPU 基线设备上加载、可玩，没有校验错误。

已知局限：色散分解是线性的，封闭海湾里厄塞尔数超过 100 的 2.4 m 长涌浪会让湾内能量在约两分钟后增长，
所以冲浪样例改用非静水压模型。水深不足 1 m 处，短于几倍水深的涟漪按长波波速传播，略快。非静水压在
512×256、4 子步时每步 6.6 ms（冲浪样例取 2 子步，约 3.5 ms），高于浅水方程的 1.7 ms。入水冲击只给出
von Kármán 的合力，H. Wagner（1932）的水面堆高与局部冲击压力分布未纳入；转动的附加惯量和沿水面滑行的
附加质量也未纳入。物体与水仍按步交替耦合，能量一致靠浮体一侧在同一步里补上自己的水头，而不是整体隐式
求解。

## 2. 定位

Amoris 是一个 **agent-native** 的 3D 游戏引擎。agent 在三个角色上都是一等公民，并且与人类使用
同一套接口：

| 角色 | 含义 | 引擎提供什么 |
|---|---|---|
| agent 当开发者 | 读写场景、脚本、资源，构建并验证游戏 | 一张命令目录（类型化、带 JSON Schema、拒绝未知字段并给建议），编辑器也只用它 |
| agent 当玩家 | 在运行中的世界里，以受限感知和意图式动作玩游戏 | 按 observer 投影的感知层、意图与 affordance、显式时间模型、决策时暂停 |
| agent 当调试者 | 定位"为什么"：断点、单步、数据断点、因果链、时间回溯 | 与人类共用的调试核心：人用 Chrome DevTools / VS Code / 编辑器，agent 用 MCP 工具 |

所有者 2026-10-04 给出的目标：

- **最强的 agent 原生能力**：agent 玩游戏、开发游戏、调试游戏。CLI 与架构比 MCP 更重要：agent
  通过 shell 使用工具最顺手、最省 token；MCP 只是同一命令目录的薄投影。
- **渲染与物理性能比肩 Unity 与 UE5**。
- **web 渲染性能比肩 three.js**。

本轮必须证明五件事（所有者 2026-10-03 的要求）：

1. **性能**：渲染与物理比肩 Unity/UE5，web 比肩 three.js。同机对照测量：Bevy 0.19（Rust/wgpu 的前
   沿）、three.js WebGPURenderer（web）、Jolt（物理，Godot 4.6 起新项目的默认 3D 物理）（第 6 节）。
2. **agent-native gameplay**：LLM agent 通过 MCP、在受限感知下玩通游戏；脚本里的决策模型每秒做
   上百次决策；fork 前瞻。
3. **web 渲染与神经渲染的先进性**：同一渲染器在浏览器 WebGPU 上运行；3D Gaussian Splatting 与神经
   纹理（着色器内 MLP 解码）作为渲染器的一等特性。
4. **编辑器的现代性与完整性**：可停靠的多面板 Web 编辑器，视口即引擎本身，层级、检视器、Gizmo、
   资源、脚本编辑与调试、时间线、性能分析、agent 面板齐备。
5. **断点调试与 agent 原生调试的流畅性**：TypeScript 源码级断点（含条件断点、单步、局部变量、帧上
   求值）在真实的 Chrome DevTools 与 VS Code 中可用；同一调试核心以 MCP 工具暴露给 agent，并有
   引擎级的数据断点、因果追溯与时间回溯。

## 3. 原则

1. **同一接口**。编辑器、agent、脚本、测试使用同一张命令目录；编辑器没有特权通道，所以人能做的
   agent 都能做，反之亦然（`Amoris Pioneer` master 验证过的做法）。
2. **感知是游戏定义的一部分**。每个 observer 经同一感知层取信息（有范围、遮挡、注意力）；全知视图
   必须显式标记，只给调试与评测。观察以拉取为主，事件推送差量，每次调用支持 token 预算。
3. **状态全在世界里，由运行时强制**。游戏状态只存在 ECS 组件里；脚本是无状态系统，冻结的全局、
   lint 与重载等价检查共同保证。
4. **确定性、fork、replay 是一等能力**。固定步长，同种子同输入逐 tick 同哈希；fork 是按需能力
   （前瞻、测试、编辑器 Play、调试回溯），不进入每 tick 的执行路径；replay 能定位首个分叉 tick。
5. **意图式动作与结构化错误**。错误是 `{code, message, detail}`；未知参数整调用拒绝并给出"是不是
   想写……"。
6. **LLM 不在 tick 内**；决策模型（脚本或原生策略）可以在 tick 内，以每秒上百次决策运行。
7. **数据导向的性能**。脚本按列批量处理（typed array），重活在 Rust 系统里；渲染以 GPU 驱动为
   目标，没有静默容量上限。性能测量随提交记录，用来发现退化与指导优化，不作为通过门槛。
8. **结构整洁**。按职责划分模块与 crate，依赖单向并由检查命令核对；不设文件行数上限。
9. **不维护文件核对哈希清单**。2026-10-10，所有者要求移除共享文档、素材、展示与评测的
   文件哈希记录，减少重复维护。来源保留仓库、提交、日期与授权信息；`shared/SYNC.toml`
   只记录可选来源提交。生成文件和 vendored 源码仍可重建后逐字节比较，不另存核对基线。
   运行时的内容身份、世界哈希、snapshot/fork/replay 与依赖锁的供应链完整性机制保持不变。
10. **运行产物不入库**。常规日志、逐帧数据、原始测量与一次运行的报告放在忽略目录 `out/` 或
    CI artifacts；经隐私与凭据清理的公开产物归档到独立的
    [amoris-benchmarks-results](https://github.com/qiulinfan/amoris-benchmarks-results) 仓库。
    引擎仓库保留测试源码、固定夹具、benchmark 源码及简明结果表和方法。

### 4.2 脚本：TypeScript on QuickJS-ng

- 脚本是数据导向的**无状态系统**：声明查询，按列（typed array）批量读写组件；组件可以在 TS 里
  声明（字段类型、默认值、文档），与引擎组件同为一等公民。写入在 tick 内暂存，整体校验后提交。
- 转译：oxc 在进程内去类型并产出 source map；类型检查交给 TypeScript 7（`tsc --noEmit`），只用于
  反馈，从不在运行时执行。
- QuickJS-ng 0.16.2 以 vendored 的 `rquickjs-sys` 0.14.0 构建，带：
  - **PR #1421**（`JS_SetDebugTraceHandler`、`OP_debug`、局部变量与帧上求值）：断点调试的基础。
  - **P1–P8**：确定的中断计数预算、不可捕获的栈溢出与 OOM、常量哈希种子、`-ffp-contract=off`、
    每上下文调用深度上限、typed array 的规范 NaN、构建修正、失败调用丢弃挂起的 promise 任务。
  - **P9–P10**（调试器，2026-10-04）：被跟踪函数的语句位置缓存（插桩后每条语句的开销从约 16 ns
    降到约 4 ns）；异常进入 trace 回调并附带是否会被捕获的预测，以及任意栈帧的位置查询。
  - **P11**（2026-10-10，采用 Amoris Pioneer 的调试修复）：帧上求值按暂停语句所在的
    lexical scope 解析名字。编译器记录插桩语句的作用域，不改变保留在字节码中的操作码编号；
    解决块内后声明的 `let`/`const` 无法求值以及 sibling block 局部变量外露的问题。
  - **P12**（2026-10-15（Pioneer））：原生 Windows 构建用 computed goto 分派字节码。quickjs.c 一见
    `_MSC_VER` 就关掉 computed goto，而 clang-cl 也定义 `_MSC_VER`，所以原生构建一直走 `switch`；
    clang-cl 支持 labels-as-values，P12 只对 `_MSC_VER && __clang__` 打开它（MSVC 的 cl 与 wasm32
    仍用 `switch`）。理由：脚本 tick 的大头是解释执行，而 computed goto 是 QuickJS-ng 在 clang 与
    GCC 上的默认分派，原生 Windows 只因这一宏判断而错过；它不改变语义：中断轮询（步数）与 P5 的
    深度计数都在分派之外，世界哈希与步数不变。
  - **P13**（2026-10-16（Pioneer））：跳转指令（`OP_goto`、`OP_if_true`、`OP_if_false` 及其短形式）
    的中断轮询在计数耗尽、调用中断回调之前，先把本帧的 PC 记为这条跳转指令。理由：脚本的步数剖析
    （4.3）以步数计数器为采样时钟，在中断回调里经 P10 的 `JS_GetStackFrameInfo` 读调用栈；上游只在
    调用与会抛错的慢路径上保存帧的 PC，所以跳转处读到的是本帧上一次调用的位置（循环体里没有调用时
    为空），按行统计会把多数步数记到别的行上。快速路径做的事不变（计数减一、比较、跳转，只调换次
    序），计数到期才走慢路径；预算耗尽的异常照旧从跳转目标展开，错误位置、步数与世界哈希都不变。
  - 2026-10-16（所有者决定）：P12 与 P13 保留为本地的 QuickJS-ng 补丁，由所有者评审。代理从不向上游
    提交 PR；所有对外部项目的 PR 都由所有者本人提交（上文与
    [script-sandbox.md](spec/script-sandbox.md) 4.2 所说"提议给上游"的补丁同样如此）。
- 预算：每系统 100 万步、每 tick 200 万步、64 MiB 内存；步数不进入世界哈希。
- 性能定位：解释执行比同等 Rust 规则慢 21–27 倍（Amoris Pioneer 的 script-native spike）。对策是让脚
  本做编排、让引擎做重活：物理、动画、寻路、感知、渲染都在 Rust 里，脚本经批量列接口调用。与 Godot
  的 GDScript 处在同一量级，与 Unity C# 有差距；JIT 后端作为测量实验列入排期，不进入本轮默认路径。
  2026-10-14（Pioneer；数字为 2026-10-15 的安静复测：其他代理已结束，整次测量持机器的测量锁，各轮前
  CPU 负载 3–7%，五轮交错，共跑两次）：首次在引擎内测同一负载。`bench/rules` 经真实宿主
  （`install`、`swap`、`Sim::step`）运行，对照同引擎内逐 tick 世界摘要完全一致的 Rust 孪生实现：原生
  tick 中位数 3.6 ms，是孪生的 27 倍（只计系统本身 31 倍）；wasm32 在 Chrome 155 的 worker 与 Node
  25 中为 3.1 至 3.3 ms，是孪生的 20 至 21 倍。按现行的两套发布配置，wasm32 比原生 release 还快，原
  因未分离（两者的 Rust LTO、QuickJS-ng 的 C 优化级别与分配器都不同；解释器分派相同，都是
  `switch`）。21–27 倍的量级成立，原生在上沿，web 在下沿或略低于下沿。脚本 tick 约五分之一花在批量接
  口的边界上（查询准备、写回比较、写回应用），约五分之四在 `run` 中：解释执行加上规则调用的原生函数
  （约 3,000 次引擎的 `Math.sin`、`Math.cos`，`ctx.emit` 的事件数据转换，`ctx.rng.fill`），本测量未
  把两者分开。所以五分之四只是 JIT（第 8 节第 1 项）能赢回部分的上限；按 spike 测得的每次 `Math` 调
  用成本估算，解释执行约占三分之二。方法与数据见 [bench/script.md](bench/script.md)。
  2026-10-15（Pioneer；数字为同日 16:03–16:16 的安静复测：其他代理已结束，每次测量全程持机器的测量
  锁，各轮前 CPU 负载 3–6%，五轮交错，主对比跑两次；取代上午其他代理构建期间的临时数字）：上文“C
  优化级别不同”有误，clang-cl 的 `-O2` 在编译器内部就是 `-O3`，与 wasm32 相同。真正不同的是五个
  MSVC 默认代码生成选项（不做基于类型的别名分析、`errno` 数学、`/GS` 栈保护、有符号溢出回绕
  `-fwrapv`、`volatile` 的 acquire/release 语义），其余差别属于平台本身；五个都改成 wasm32 的取值后
  没有收益，反而略慢（tick 慢 1.4%，`run` 慢 1.9%），不采用。上文按 spike 的每次 120–134 ns 估算
  `Math` 调用，同一硬化上下文中实测闭包为每次 88–89 ns，约 3,000 次合 0.27 ms。P12 让原生解释器改用
  computed goto，`run` 快 3–5%，tick 快 2–4%：孪生实现在两者之间不漂移，这个收益可以分辨（临时数字
  时未分辨），但它与重新构建本身造成的约 2% 差异（未改动的孪生在另一构建中快约 2%，推测是代码布
  局）同量级，很小。引擎的 `Math` 函数（`hypot` 除外）改为 QuickJS-ng 的 C 函数（不再经 rquickjs
  的闭包跳板）后，`Math.sin` 每次调用 33–36 ns，`run` 再快 5–6%；三项合计原生 tick 中位数 3.36 ms，
  比改动前快 6–9%。安静复测推翻了有负载测量中“原生 `run` 与 wasm32 持平”的结论：原生 `run` 仍慢 5–9%

  写回应用多 62–72 µs、`run` 多 132–214 µs。持平是负载拖慢 wasm32 宿主更多所致。查询准备也运行
  prelude 的 JavaScript、在 QuickJS-ng 里分配 typed array，并非全是宿主 Rust。见 bench/script.md
  第 7 节。
  2026-10-16（Pioneer；数字为同日 03:08–03:10 的安静复测：其他代理已结束，测量全程持机器的测量锁，各
  轮前 CPU 负载 3–8%，五轮交错；取代 2026-10-15 晚间其他代理构建与测量期间的临时数字，结论不变）：

  给出上下界），取各轮中位数：`run` 2.57 ms 中，原生函数 0.83–0.85 ms，其余 1.72–1.74 ms 是解释执行
  （含 QuickJS-ng 自己的内置函数和调用原生函数的开销），按各轮自身占比的中位数为 `run` 的
  67–68%、tick 的 51–52%。原生函数几乎全是 5 次 `ctx.emit` 的事件数据转换（4 个 `combat.damaged` 事
  件各带四个最多 250 个数的数组，每个约 0.2 ms；另有 1 个很小的 `combat.died`），约 3,000 次 `Math`
  调用只占 25–47 µs。所以在 QuickJS-ng 里，即使解释执行降到零，tick 也只快约 2.1 倍。这个上限只对
  QuickJS-ng 成立：其余部分并非与引擎无关，查询准备运行 prelude 的 JavaScript，事件数据转换经
  QuickJS-ng 的对象 API 逐个元素按属性名读取；换成 V8 或浏览器自身的引擎，这两部分是另一套代码，代价
  没有测。可以确定的是，在本引擎里，占 tick 近四分之一的事件数据转换不靠 JIT 也能先优化。步数剖析

  位，不等于时间。见 bench/script.md 第 8 节。

  rquickjs 闭包的缺少参数错误，与 QuickJS-ng 自己的内置函数一致

  ms，p99 3.65–4.02 ms，bench/script.md 7）不取代它们。

### 4.3 调试

一个调试核心，三个前端：

| 前端 | 使用者 | 协议 |
|---|---|---|
| Chrome DevTools、VS Code（js-debug attach） | 人类 | CDP（Chrome DevTools Protocol）端点，127.0.0.1；TS 源码映射由客户端按 source map 完成 |
| 编辑器（Monaco 的断点栏、调用栈、变量、监视、控制台求值） | 人类 | 同一个 CDP，经 WebSocket |
| MCP 工具：`debug.*` | agent | 结构化 JSON：暂停时的调用栈、局部变量、组件、事件 |

- 断点在游戏线程的 trace 回调里暂停；渲染与服务线程继续工作，暂停期间编辑器仍可观察世界。
- 只有调试器连接时才插桩：连接与断开时在 tick 边界重编译脚本（脚本无状态，热更新使之廉价）；
  未连接时零开销。
- 引擎级调试（agent 原生）：组件字段的**数据断点**（某字段被哪个系统改写时暂停）、`events.why`
  因果链、tick 环形快照与**时间回溯**（恢复到任意 tick 重放到断点）、两次运行的**首个分叉 tick**。
- 2026-10-15（Pioneer）：数据断点里引擎系统的一半先以**写入追踪**交付：`debug.writes`（即
  `time.step {trace}`）不暂停游戏，逐 tick 列出改写某字段的每个系统（引擎系统与脚本系统，脚本系统附
  写入语句的 TypeScript 位置）和该 tick 边界上记录的写入。原因：引擎系统是 Rust 代码，停在其中没有可
  检查的帧；调试器 6 节的数据断点（`debug.watch`）只看脚本系统的暂存写入；agent 要回答的是“谁改了
  它”，调试评测的第 5 项要求的正是不暂停的写入追踪。为此 `StepHooks` 增加每个系统前后的只读世界视
  图；追踪开启与关闭时世界哈希相同。暂停式的引擎级数据断点仍未实现。
- 2026-10-16（Pioneer）：脚本的**步数剖析**：`scripts.profile {ticks, interval}` 在世界的 fork 上运
  行若干 tick，世界本身不动；以步数计数器（P1）为采样时钟，每 `interval` 步在中断回调里记一次调用
  栈，经 source map 映射到 TypeScript 的函数与行，按系统给出精确步数，按函数与行给出自身与累计步数
  （按样本估计，interval 为 1 时即精确），并给出折叠栈（speedscope 可读）。剖析开启与关闭时步数、预
  算的停止点（包括正则表达式触发的停止）与世界哈希相同；同一状态的剖析逐字节相同，原生与 wasm32 相
  同。原因：agent 要知道哪些 TS 行花掉步数（步数正是预算的单位），按毫秒采样的剖析不确定、无法复现，
  也无法与预算对照。为此新增补丁 P13（4.2）。

  于是透过 alpha 0.5 的面板只传到应有遮蔽的约 0.69，面板自身的光也被压暗（复审测得每像素约 3.8%），
  而 RTX 5060 的默认配置正是 MSAA 加 GTAO；先环境光遮蔽、后半透明是通常的顺序，代价是这些帧多一个通
  道，多重采样的颜色要存下样本再载入，粒子与编辑器网格在这些帧里也不再被 GTAO 压暗（此前它们按背后的
  占比被压暗，也不对）。透明管线原先在首个出现透明实例的帧上按需建造，Direct3D 12 上该帧与每次切换抗
  锯齿或 GTAO 后的首帧在渲染线程上卡顿约 100 ms（DXC 编译）。永不投影的透明实例原先也画进每个级联，
  片元全被丢弃，在 1,000 个球的测试中约占其 GPU 开销的四分之一。测量（复审后，2026-10-16 在空闲机器
  上复测）：GPU 测试中，面板前后 GTAO 拿走的光之比为应有的 1.0013 至 1.0014 倍，原先的顺序放回测试即
  不通过；RTX 5060（MSAA 加 GTAO）上把透明阶段移到 GTAO 之后的开销在 0.03 ms 以内，不再画永不投影的
  投影者省 0.11 ms（780M 约 0.2 ms）；Direct3D 12 上首个透明帧的编码时间由 110.0 与 108.8 ms 降到
  14.1 与 8.5 ms（与没有透明实例时相当），启动时间没有可见的变化。
- **神经渲染**：
  - 3D Gaussian Splatting：预处理计算着色器（投影、剔除、球谐取色）、GPU 基数排序、实例化四边形混
    合，与网格深度缓冲合成，即混合网格与 splat 的场景。 2026-10-09（Pioneer）：另有可选的计算着色器
    分块光栅化，与实例化四边形并存，默认仍为四边形。它把可见 splat 按 16x16 像素分块分箱，稳定排序后
    每个分块保持由前到后的深度序，逐块由前向后混合，像素饱和或到达网格深度即停止，只用 WebGPU 核心特
    性。理由：四边形路径受填充率限制（M5 上 3M splat 的绘制 21–30 ms），分块是参考实现的做法；在 RTX
    5060 上两者互有胜负（3M 与 2560x1440、近景时分块快 12–20%，1M/2560x1440 时快 3–13%，3M/1600x900
    时持平， 1M/1600x900 时四边形快约 10%，抗锯齿模式与远景时四边形快 20–90%；除远景外分块的光栅本身
    都比四边形绘制快，差距来自分箱与第二次排序。同日更正：先前一组测量误用了关闭子块剔除的着色器），
    默认值待参考机测量后再定（见 `docs/spec/splats.md` 4.2 与 `docs/bench/splats.md`）。
    2026-10-10（Pioneer，安静环境重测之后）：默认光栅化由测量决定，所有适配器都用实例化四边形
    （`SplatRaster::DEFAULT`），分块光栅化保留为可选（`AMORIS_SPLAT_RASTER=tile`）。理由：在 RTX
    5060 与 Radeon 780M、Direct3D 12 与 Vulkan 上五轮交错测量 1M 与 3M 花园（1600x900 与
    2560x1440）、球谐近景、抗锯齿模式与 2.5 倍距离：花园的默认视图（1M、1600x900）上分块的 GPU 时间
    是四边形的 1.09–1.47 倍，每种适配器与后端都更慢；抗锯齿与远景 1.24–2.06 倍；分块只在 3M 或
    2560x1440 与近景时更快（0.79–0.97，多在独立显卡的 Vulkan 上）。集成显卡上分箱与第二次排序很贵
    （1M 时约 7.6 ms），除 Direct3D 12 上 3M、2560x1440 一处（0.95）外处处更慢。没有一种适配器类别上
    分块明显占优，故不按适配器区分。测量中还发现分块的逐像素遍历在 NVIDIA 的 Direct3D 12 上慢 8 倍
    （循环里的 break/continue；1M 时 11.4 对 1.45 ms），改为由循环条件结束后与 Vulkan 相当，画面逐字
    节不变（Radeon 780M 上这一改动使 Direct3D 12 快 1.5 倍、Vulkan 慢 7%；同日复核的证据见
    `docs/evidence/quiet/splats/walk/`）。 Apple GPU（四边形的混合在其上最贵）未测量；若 M5 上分块明
    显更快，再为 Apple 另定默认值。见 [bench/splats.md](bench/splats.md) 的安静环境重测一节。
  - 神经纹理压缩：材质的多通道纹理压缩为低分辨率潜变量网格加一个小 MLP（Python/PyTorch 训练），
    在片元着色器里逐像素推理解码；对比未压缩与传统压缩的体积和质量。
    2026-10-09（Pioneer）：神经纹理的训练改在引擎自己的 wgpu 计算着色器里进行，不用 Python/PyTorch：
    离线编码器是 `amoris-render` 的一个 cargo 示例，手写前向与反向传播（与在线 NRC 同样不用浮点原子
    操作：潜变量梯度以定点整数原子累加，与顺序无关，MLP 梯度按固定顺序分块归约），同一种子的结果
    可复现。编码结果是带版本号、严格校验的二进制文件（`.ntex`），类型在 `amoris-assets`（游戏侧，
    可编译到 wasm）；`Model.material` 写 `.ntex` 路径即为神经材质，渲染输入流的格式不变。神经材质
    走自己的管线变体，其他材质的着色器与绘制不变；有 `SHADER_F16` 时以 f16 解码，否则 f32，
    WebGPU 基线与浏览器同样运行。理由：本机没有 PyTorch（CUDA 版约 3 GB 下载）；训练与运行时解码
    共用同一套 WGSL 约定，编码器在 Metal、Vulkan、Direct3D 12 上都能跑，不再需要另一套语言与
    运行环境；网络很小，手写反向传播可行（在线 NRC 已验证这种做法）。BCn 对照用 crates.io 的
    CPU 编码器（只作工具层的开发依赖）。规格见 [神经纹理](spec/neural-textures.md)。
    暂定测量（2026-10-09，机器上同时有其他工作）：8 至 12 通道的材质 5.37 bit/texel（含全部
    mip，为 BC1/BC5/BC4 的 1/4 至 1/6）；四种程序材质的 mip 0 为 40 至 52 dB，七种材质中六种的
    每个通道组都高于半分辨率的 BCn，mip 2 低 5 至 11 dB；2560x1440 全屏解码在 RTX 5060 上 f16
    约 3 ms，Radeon 780M（Direct3D 12）上约 10 ms，Chrome 中与原生相当。见
    [测量记录](bench/neural-textures.md)。
- 浏览器 WebGPU 与原生 Metal/Vulkan/Direct3D 12 走同一份代码；只使用 WebGPU 默认可用的特性作为基线，
  原生可选特性（如 multi-draw indirect、时间戳查询）作为加速路径。

### 4.5 编辑器

- 形态：Web 应用（TypeScript + React + Vite），由宿主在 127.0.0.1 上提供；桌面版使用 Electron
  打包相同界面。所有者 2026-10-05 授权桌面 GUI：选用随应用分发的 Chromium，固定 WebGPU
  运行环境；原生菜单、目录选择器和宿主生命周期由桌面主进程负责。此项替换此前待实施的 Tauri
  包装计划，不更改模拟、渲染器或命令接口。实现与验证见 [desktop.md](spec/desktop.md)。
- 视口：引擎渲染器编译到 wasm，在页面里用 WebGPU 绘制；场景由宿主经 WebSocket 推送快照与差量，
  资源经 HTTP 获取。原生窗口（Metal/Vulkan）用于独立运行与 Play。
- 权威：唯一权威是宿主进程里的世界。编辑器的每次修改都是一条命令，进入可撤销的事务历史；agent
  经 MCP 的修改进入同一历史。
- 面板：层级树、检视器（由 JSON Schema 生成）、视口（拾取、平移/旋转/缩放 Gizmo、吸附）、资源
  浏览器、脚本编辑器（Monaco，诊断与断点）、调试（调用栈、变量、监视）、控制台、事件与因果、
  时间线（tick 拨动、快照、回溯）、性能分析、agent 面板（agent 的操作流与对话）。
- 2026-10-14（Pioneer）：性能分析面板接上真宿主，分两半实现。4.1 表中“每个渲染通道的 GPU 时间戳推送
  到编辑器”假设由宿主渲染，而编辑器的视口是页面里的 WebGPU，宿主不画帧，所以 GPU 通道时间戳与帧间隔
  由编辑器从自己的视口读取并入。宿主一侧：服务 profile 流的宿主（`amoris serve`）运行期间，游戏线程
  从启动起用 step hooks 以循环的注入时钟计时每个 tick 的系统（脚本系统从 `script.update` 中单列）与
  阶段，加上 tick 之后循环的工作（渲染流提取，快照与流的发布，玩家决策点与 `time.step` 的检查），写
  入 amoris-link 的 profile 环；环只保留当前世界的 tick（Play、Stop 与回溯清空它），游戏线程写环时从
  不等读者。`amoris run` 与原生窗口不服务 profile，也不计时。服务端每 250 ms 推送
  `profile`，`profile.frame` 让 CLI（`amoris profile`）与 MCP 读到同一份数字。调试器停住的 tick 计数
  但不计入时间。规格见 [server.md](spec/server.md) 第 4 节，测量见
  [bench/profiler.md](bench/profiler.md)。
- 被否决：egui（所有者要求 TS + React）；把编辑器 UI 做成引擎自己的 UI 系统（Amoris Pioneer master
  的 Pocket UI，效果与工作量不划算）；视口按 PNG 轮询推帧（Amoris 原型，4 Hz）。

### 4.6 构建链

- Cargo workspace 加 `cargo xtask`（检查、代码生成、vendoring、web 打包）。不自研构建系统：
  Amoris Pioneer master 的 `pocket` 工具（Rust 写的第二套构建系统，嵌入 n2 后又换回 Ninja）在 Cargo
  之上重复了增量构建、特性与目标管理。
- TypeScript 包（`sdk/`、`editor/`）用 bun 安装与运行脚本，Vite 打包编辑器。
- web：`wasm32-unknown-unknown` + wasm-bindgen + wasm-opt；QuickJS-ng 的 C 代码用 wasi-libc 编译。
- 2026-10-16（所有者决定）：GPU 测试矩阵进入 `cargo xtask check`，作为 `test` 之后的一步
  （`tools/gpu_matrix.py`，[bench/gpu-matrix.md](bench/gpu-matrix.md)）：渲染器的 GPU 测试在本机每块
  GPU 适配器的每个原生后端上运行，加上 auto 配置（不设 `AMORIS_BACKEND`，比较后端的测试在同一进程里
  跑遍原生后端）和一块适配器上的 WebGPU 基线设备；跳过的测试逐项列出，跳过不算通过；任何失败或"找不
  到 GPU"都使这一步失败；没有 GPU 适配器或无法运行该工具（例如没有 Python）的机器上这一步跳过并写明
  原因。步骤的细节见 [checks.md](spec/checks.md) 4 与 [bench/xtask.md](bench/xtask.md)。
  实现后（Pioneer，同日）：这一步补上的是：`test` 只在默认适配器上运行渲染器的测试（默认后端；比较后
  端的测试另在其他原生后端上运行），其他适配器上的失败不会出现（wave 4 在 Radeon 780M 上发现了
  master 上失败的测试，bench/gpu-matrix.md 2 与 3），缺少 GPU 或能力而跳过的测试在那里也静默通
  过。`gpus` 步骤运行 `tools/gpu_matrix.py --configs machine --workspace`：渲染器的一项测试列出各原
  生后端上的适配器，工具据此在每块硬件适配器的每个后端上、在默认适配器以外的适配器的 auto 配置上、以
  及默认适配器的默认后端上的 WebGPU 基线设备上运行；默认适配器的 auto 配置就是 `test` 步骤的运行，略
  去。测试二进制按 `cargo test --workspace` 构建（只构建 amoris-render 时其依赖的特性不同，要再构建
  一遍），在 `test` 之后无需再构建。R1 上 6 个配置、每个 191 项测试：1,135 项通过，11 项跳过（全在
  WebGPU 基线设备上），用时 8 分 58 秒（其他工作线同时在构建，不是安静测量）。见
  [bench/gpu-matrix.md](bench/gpu-matrix.md) 11 与 [checks-slice1.md](spec/checks-slice1.md) 24。
  复审后（Pioneer，同日）：测试二进制以错误退出而没有测试失败（例如测试都报告通过后崩溃、列出测试超
  时），或在某个配置里没有列出测试，也使这一步失败（`gpus.binary_failed`），与 `test` 按
  `cargo test` 的退出状态判定一致；跳过的测试超过报告每步 20 条警告的上限时，最后一条
  `gpus.more_skipped` 给出其余的数目，`out/check/gpus.json` 列出全部；`test` 在同一次检查里没有运行
  （`--only gpus`、`--skip test`），或环境设置了 `AMORIS_ADAPTER`、`AMORIS_BACKEND` 或
  `AMORIS_GPU_MINIMAL` 时，这一步自己运行默认适配器的 auto 配置（`default-auto`）。`--only gpus` 复
  测：7 个配置、每个 192 项测试，1,333 项通过，11 项跳过，用时 10 分 4 秒（同样不是安静测
  量）。master 在 `6af291db` 的完整检查不含这一步已用时 15 分 16 秒，超过
  [budgets.md](spec/budgets.md) 5.5 中 `check.full` 的 900 秒；这个数字是否调整由所有者决定。

### 4.7 物理性能与后端

所有者要求物理性能比肩 Unity（PhysX）与 UE5（Chaos）。Rapier 在确定性配置下关闭了 SIMD 与并行，
吞吐量是风险点。做法：在同一台机器上用同一组场景（箱子金字塔、大量球体、布娃娃、射线查询）测量
Rapier（确定性配置、SIMD+并行配置）与 Jolt（原生 C++ 构建，其跨平台确定性选项开与关），据此决定：

- Rapier 足够：保持单一后端；
- Jolt 显著更快：`amoris-physics` 抽象出后端接口，原生默认 Jolt（经 C 封装），web 与确定性检查
  继续用 Rapier，或以 Jolt 的 wasm 构建统一。

2026-10-16（Amoris 集成）：采用同机物理对照的工具和场景验证方法，保留 Rapier 为运行时后端。
PhysX 的结果仍在 Pioneer 私有记录中，未获公开许可的数值不进入本仓库；工具、方法和适用边界见
[physics-r1.md](bench/physics-r1.md)。这次集成不据此宣称已达到 PhysX/Chaos 的性能目标。

2026-10-15（Pioneer）：物理缓存改用第 2 版布局（`layout 2`），固定刚体碰撞体的形状不再写进缓存的字
节。第 1 版把 Rapier 的整个 `PhysicsWorld` 写成缓存，关卡级的三角网格因此在每个快照、每 tick 的哈希
与每次 fork 里都再写一遍，而它本来就在持久化的 `Collider` 组件里：999,698 个三角形的地形使缓存达到
102.3 MB，一次 fork 原生约 0.16 s（physics.md 列为 Rapier 一方的第一项）。现在，固定刚体的形状只要是
由它仍未改动的 `RigidBody` 与 `Collider` 组件构建的，缓存就只写一个按引用的槽位（刚体携带的 64 位规
格哈希，加上这两个组件字节的 BLAKE3 摘要），恢复时取同一形状或由恢复出的组件构建它；其余形状照旧内联
写入。缓存字节的含义因此也取决于形状的构建代码，所以缓存身份多了一个构建版本号（`shapes 1`），构建结
果由一个金值测试与原生/WebAssembly 报告的对比守住。一个随代码提交的测试断言：逐 tick 的轨迹（缓存以
外各节的哈希）与第 1 版布局逐位相同，变的只是缓存的字节。代价是冷恢复（新进程载入存档，或已没有世界
持有该形状时）变慢：它要重建网格与 BVH，999,698 个三角形时比第 1 版原生慢约 0.18 s，WebAssembly 慢约
0.36 s。

2026-10-16（Amoris 集成决定）：采用不可变碰撞形状的进程级弱引用表。表只缓存由组件内容构建的几何，以
BLAKE3 为键，不含模拟状态；Rapier 修改形状前复制，世界之间不共享可变状态。缓存命中只改变恢复成本，不
改变结果，因此与 4.1 的 fork 自包含要求相容。接受冷恢复重建 BVH 的成本，并以形状修改后隔离、冷恢复和
逐 tick fork 轨迹测试约束它。物理后端仍为 Rapier；本次不采用未经完整引擎复测的 Jolt 迁移结论。反序列
化的泛型形状守卫直接使用既有传递依赖 `typeid =1.0.3`，依赖理由见架构表。百万三角形关卡的组件规格哈希
仍是瓶颈，缓存瘦身不解决该问题。


### 4.8 2026-10-10 的 Amoris 平台复核

本次整合保留 Pioneer 的 Windows 测量及其原时间，但在 Amoris 的 M5/Metal 上重新验证实现。
LOD 的径向距离不能保证离轴透视投影的像素误差；整合时改为包围球的最近轴向深度与投影导数
上界，保持 1 像素设定与 20% 误差迟滞，不放宽轮廓测试。splat tile 的共享向量分量写入存在
数据竞争，改为同布局的独立标量字段，消除 Metal 上的闪烁。当前 wgpu 30.0.1 的 Metal
加速结构 barrier 没有实现（[wgpu #9215](https://github.com/gfx-rs/wgpu/issues/9215)），
光追阴影在该后端按已完成的构建提交排序；光追片元着色器与 4 倍 MSAA 的组合在 M5 上持续
黑帧，因此该路径使用单采样，可保留 TAA。普通 Metal 渲染仍使用原采样设定。仅在修复后的
wgpu 通过本机冷启动、移动、蒙皮与多采样回归后移除这些约束。平台修复和实际验证另记于导入说明。

### 4.9 方块体积与第一人称身体（2026-10-17）

2026-10-17，所有者决定引擎与游戏一起开发：游戏放在独立的公开仓库
[amoris-samples](https://github.com/qiulinfan/amoris-samples)，开发游戏时发现的需求由引擎原生支持，
不在游戏里绕开。第一个这样的需求来自其中的 blockcraft（方块沙盒）：玩家能在静态世界里走，却不能挖
方块、放方块。原因有四个：行走相机是 presenter 一侧的状态，不在世界里；脚本收不到指针输入；脚本既
不能改几何，也不能发射线；行走碰撞只在加载时从场景文件建一次。

决定（所有者 2026-10-17 接受，规格见 [voxels.md](spec/voxels.md)）：

- **方块体积是世界状态**。新增引擎组件 `Voxels`，放在 `amoris-sim`：16³ 的区块、至多 256 种方块的调
  色板、可选的初始格子文件；按原则 3 和原则 4，编辑都经由组件，进入快照、世界哈希与 replay。区块按字
  节编码；未编辑的 tick 由 `SnapshotCache` 复用整节，编辑的 tick 重新编码整节（blockcraft 约 1.3
  MB）。
- **脚本经 `ctx.voxels` 读、改、发射线**：get、set、fill、block 与精确的网格射线（DDA）。写入在系统
  返回时生效，与 `world.set` 一样。
- **第一人称身体与方块的碰撞按方块游戏自己的做法**：身体是轴对齐的盒子，按 y、x、z 依次与固体格子扫
  掠裁剪，精确、确定、不需要 Rapier 状态。实现时修订（2026-10-17）：原提议在 Rapier 世界里放 parry
  的 `Voxels` 形状，但求解器以 Rapier 自身字节作为 Cache 节持久化，体素形状会写进每个快照
  （blockcraft 约 1.3 MB），除非缓存像固定 `Collider` 那样按引用写形状、恢复时从组件重建。这项扩展留
  作下一步，届时动态刚体与物理射线才与方块体积碰撞；本切片的身体与脚本不依赖它。
- **第一人称身体在世界里**。新增持久组件 `Walker` 与 `physics.walk` 系统：在 tick 内移动身体，实体的
  `Transform` 即眼睛。新增引擎动作目录 `first_person`：一个 seat `player`，控制移动、视
  角、奔跑、快捷栏，并以无目标的 pulse 表示跳跃、主键和副键。按原则 1，窗口前的人与经 MCP 的 agent
  使用同一套 `player.act`；这些输入都被记录，挖放方块可以逐 tick 重放。
- **渲染器自己生成区块网格**。渲染输入流只传变化的区块（`FORMAT` 随之改变，viewport 重建入库）。渲染
  器剔除隐藏面、按材质分组，把区块作为普通网格与实例交给场景，所以剔除、阴影、TAA、拾取、透明与镂空
  都照常工作。`MeshPool` 增加原地替换：键与行号不变，旧区间进空闲链表供后来的网格复用（实现时修订，
  原提议为 `remove`）。
- presenter 一侧的 `WalkController` 原样保留给没有 `Walker` 的游戏（如 town-walk）。

不在本切片内：agent 对方块世界的感知、带状态的方块、光照传播与平滑光照（顶点格式没有顶点色）、
流动的液体、旋转或缩放的体积、glTF `NEAREST` 采样（blockcraft 暂以最近邻放大到 1024 的贴图代替，
引擎支持该采样后去掉）。浏览器 worker 每 tick 不经缓存做快照，大体积会增加这部分开销；本切片先测量，
结果并入第 8 节第 3 项。


### 4.10 流动的液体（2026-10-17）

所有者 2026-10-17 决定：以 amoris-samples 的 blockcraft 为测试样例，探索液体模拟，改进引擎的物理系
统。blockcraft 的水是永远不动的液体格：挖开湖岸，坑一直是干的；走进海里，人像石头一样沉到底；在水
下看到的和水上一样。

决定（所有者 2026-10-17 接受，规格见 [liquids.md](spec/liquids.md)）：

- **液体按方块游戏的规则流动，做成确定的元胞自动机**（2026-10-18 起改为可选的游戏规则，引擎的水改
  为下文的高度场）。不用欧拉网格或 SPH 求解器：方块世界里，玩家预
  期的就是原版的水，而且这个模型完全是整数运算，能逐 tick 重放、fork 和恢复。每格新增一个状态字节
  （低三位是液体等级，第四位表示下落），调色板的液体条目新增流动参数（扩散距离、步进周期、找下坡的距
  离、两格水源夹出新水源）。新系统 `physics.fluids` 只处理待定的格子：编辑过的区块里的液体及其邻格，
  加上上一步变化过的格子。每一步先用旧状态算出全部新状态，再一起写入，因此访问顺序不影响结果。
- **待定列表与状态都是世界状态**，进入快照、世界哈希与 replay；一次流动可以逐 tick 重放，fork 后接着
  流。
- **Walker 在液体里会浮、会游**：重力减为四分之一，下沉速度有上限，水平速度变慢，按住空格上浮，贴着
  岸边上浮能爬上一格高的岸，流动的水会推人。
- **画面**：液面按等级高低绘制，格与格之间成坡；相机在液体里时使用该液体的雾。渲染输入流带上状态字
  节，`FORMAT` 随之改变，viewport 重建入库。

不在本切片内：Rapier 刚体浮在体积液体里（要等体积与 Rapier 刚体碰撞的工作完成）、液体之间的反应、压
力与波浪。

**水花与涌流（2026-10-17，所有者 2026-10-18 接受）**。所有者看了元胞自动机的水后判断它仍不是流体，于
是先在引擎里做了箱子水实验（[fluid-box.md](spikes/fluid-box.md)）。实验里，GPU 上的 MLS-MPM 能算出真
实的流体：坝溃、冲上对面的墙、翻卷、晃荡后归于平静。但它的浮点结果随后端而变：同一块 M5 上，Metal 与
MoltenVK 从第 1 秒起分叉，所以它不能成为世界状态。所有者 2026-10-17 选定：元胞自动机仍是规则，MPM 粒
子只做表现。

决定（规格见 [splashes.md](spec/splashes.md)）：

- **水花从液体格的变化里来**（2026-10-18 起改为由高度场驱动，见下文）。渲染器拿新收到的区块与已有
  的副本比较，有两种水花：
  - 空气格或植物格变成液体时，喷出一股粒子。下落格向下喷，其余的格从喂它的邻格那边喷出。
  - 下落水柱的底部持续溅起粒子（涌流），力度随水柱高度增加。

  以下情况都不喷：第一次收到的区块、`reset` 帧（恢复、回放跳转）、移动了的体积、离相机 48 m 以外的
  格子。每帧最多新增 2,048 个粒子。
- **粒子用箱子实验的求解器运动**：
  - 只在相机附近最多 4 个有界区域里计算，每个区域 16 格见方，每格 4 个求解器单元。
  - 方块体积的实心格挡住粒子。
  - 粒子落进同种液体的液面以下、离开所在区域、或活满 4 秒就消失。
  - 粒子池是 32,768 个的环形缓冲，满了时新粒子顶掉最老的。
- **画法沿用箱子实验的屏幕空间液面**，与粒子一样画在透明表面之后。液体调色板条目的 `flow` 新增
  `splash`（每米吸收率），没有 `splash` 的液体（例如熔岩）不溅。`BlockLook` 随之改变，渲染输入流的
  `FORMAT` 改变，viewport 重建入库。
- **只是表现**：水花不进世界、快照、世界哈希与回放，规则看到的水与此前完全相同。同一 GPU、同一后端
  上，同样的帧给出同样的水花；换了 GPU 或后端，水花可以不同。没有渲染器的宿主（headless、
  `amoris run`）什么也不算。`AMORIS_SPLASHES=off|on`（viewport 页面用 `?splashes=`）开关水花，默认开
  启。没有活粒子的帧与此前逐像素相同。

理由：方块游戏的规则需要能重放、能 fork 的水，玩家的眼睛需要会动的水。元胞自动机负责前者，GPU 粒子
负责后者，二者都已在本机验证过。确定的高度场（波浪）与确定的 CPU 粒子求解器另立切片，再议。

不在本切片内：实体落水溅起的水花、河面的流动纹理、折射、水花的投影，以及粒子推动 walker 或刚体。

**引擎的水改为确定的高度场（2026-10-18，所有者同日接受方向；补测之后写完整规格）**。所有者看了水花之
后判断：作为原版方块游戏的水还行，作为通用的物理水没有做到位；引擎的水应当通用，不该只为方块游戏而
做。当时引擎里有三种互不相通的水：海（解析的正弦波，船浮在上面，不会流动）、方块液体（照搬方块游戏规
则的元胞自动机，只存在于体素体积里）、水花（GPU 粒子，只做表现，落进水里就消失）。浅水实验
（[shallow-water.md](spikes/shallow-water.md)）在 CPU 上用确定的高度场解浅水方程，结果如下：

- 原生 release、原生 debug 与 WebAssembly 的哈希链逐位相同；
- 每列每子步原生 11 到 14 ns，WebAssembly 16 到 20 ns；
- 在方块地形上，水有动量：湖水从切口泄下，冲出平地，带走浮在上面的箱子。

所有者 2026-10-18 进一步明确：要做的是通用的物理水方案。方块游戏（MC）的水是它的一个应用特例，海洋、
河流、瀑布等也都是这同一套水的变体，由配置得出，不另做一套。

决定（规格见 [water.md](spec/water.md)，所有者 2026-10-18 审阅后接受，审阅中的决定见下文）：

- **规则层的水是确定的高度场**。新增引擎组件 `WaterRegion`（`amoris-physics`）：一块网格区域，每列存
  一个水深，每个面存一个流速，全部是 `f64`，进入快照、世界哈希与 replay。新系统 `physics.water` 每
  tick 用实验的 advect 方案推进：交错网格上的浅水方程，速度半拉格朗日平流（Chentanez 与 Müller
  2010）。只用 numeric.md 5 允许的运算，因此每个目标逐位相同。虚拟管道模型不用：它不带动量，水落地处
  会堆成水丘。
- **地形只提供每列的床面高度**。方块体积、静态碰撞体与高度图都是适配器：方块体积取每列最高的实心格，
  方块改动时重读（审阅后改为与水隔着空气的实心格不算床面，见下文第 2 条）。所以网格地形、方块世界、
  航海场景用的是同一种水。
- **方块游戏的元胞自动机降为可选的游戏规则**。液体调色板条目选择模型：`cells`（原来的规则，旧场景的
  默认）或 `field`（高度场）。选 `field` 的液体格在加载时变成高度场的水，放一格水就是往那一列加一格
  的水量。blockcraft 改用 `field`。
- **与身体和刚体相连**。Walker 用高度场的水深判断是否在水中，水流按高度场的流速推人。Rapier 刚体在区
  域内按高度场计算浮力与拖曳，区域外仍按海的波浪。本切片只做单向耦合：物体不排开水。
- **粒子层由高度场驱动**。水花从高度场的流动里生成：越过落差的水流按流量生成下落的粒子，冲击处与急流
  处生成细小的水滴和少量白沫。粒子仍只做表现，回到液面就消失，不把水量交还给高度场（高度场已经带着这
  些水）。落差处的水帘由粒子画，高度场在那里不画陡坡。
- **画面**：渲染输入流按 16 × 16 列的块只传变化的部分，`FORMAT` 随之改变，viewport 重建入库。画法沿
  用实验的高度场：按深度透明，菲涅耳反射天空，急流处有成条的泡沫。相机在水面以下时用水的雾。
- **应用例都是同一套水的配置**：
  - 方块游戏的水：方块体积作床面，`field` 液体，按块对齐的列；
  - 湖、池与洪水：任意床面上的区域，堤坝一破就是溃坝；
  - 河流：有坡的床面，上游入流（边缘入流或泉），下游出流或通海；
  - 瀑布：床面上的落差，高度场把水送到崖边，粒子画空中的水帘与落点的水花；
  - 海洋：近岸是区域，边缘由海的解析波浪驱动，涌浪进入区域、冲上海滩；远处仍是解析波浪。
- **海也是这套水**：区域的通海边缘取海的解析波浪在该处的水面与流速，所以涌浪会进入区域，冲上海滩后回
  落。区域外的远海仍按解析波浪计算与绘制，两者在边缘一致。船在区域内按高度场浮起，区域外按波浪。

理由：同一套水要同时满足规则与眼睛。规则需要能重放、能 fork 的水，高度场在 CPU 上做到了逐位确定；眼
睛需要有动量、会冲、会漫开的水，advect 方案做到了，元胞自动机做不到。高度场表达不了的空中的水交给粒
子，这样两层各管一件事。

补测：Chrome 155 的逐位一致与 M5 上的绘制开销已经测过
（[shallow-water.md](spikes/shallow-water.md)）。2026-10-18 在 R1（x86-64，Windows 11）上跑了
`tools/shallow_check.py`：两种方案在原生 release、原生 debug、Node 与 Chrome 下共 8 条哈希链，与 M5
全部一致，所以规则层的确定性成立，切片 A 可以开始。R1 上求解每列每子步原生 18 到 26 ns，WebAssembly
23 到 30 ns，比 M5 慢 1.3 到 1.9 倍；blockcraft 的 256² 区域两个子步一 tick 原生约 2.9 ms。RTX
5060（Direct3D 12）上绘制增加 0.2 到 0.6 ms 的 GPU 时间；780M 尚未测（[liquids.md](bench/liquids.md)
2）。

不在本切片内：洞穴与悬垂下的水（需要分层的高度场）、物体排开水（双向耦合）、多线程求解、液体之间的
反应、折射。

**规格审阅中的决定（所有者 2026-10-18）**。所有者逐条审阅了 water.md 草案，以下各点都按推荐决定：

1. **分四个切片做**，每个切片都端到端可运行：A 是水本身加 blockcraft（区域、`physics.water`、方块床
   面、`field` 液体、walker、脚本、渲染输入流与绘制，不含远近细节层级）；B 是由高度场驱动的粒子；C
   是河流与瀑布（入流与出流边缘）；D 是海边、浮体、碰撞体床面与远近细节层级。
2. **方块体积的床面不取最高的实心格**：与水之间隔着空气的实心格不算床面。往水里或地上放方块会抬高床
   面；水上搭桥、盖屋顶、树叶都不会删掉下面的水；拆掉床面最上面的方块会降低床面。床面因此依赖历史，
   改为持久化的状态。限制：加载时已经悬在干地上方的东西（树冠、旱桥）仍算床面，留给分层高度场。
3. **通海边缘必须在浅水里**。浅水方程不带色散，只有水深小于波长的二十分之一时波速才准。通海边缘各列
   的静水深不得超过海上最长波的二十分之一（否则报 `water.deep_edge`）；高度场只承载足够长的波，更短
   的波只进法线。草案里的 `water.short_waves` 错误随之取消。
4. **区域每边最多 512 列**（512² 在 8 个子步时一 tick 约 26 ms）。切片 A 先测水不睡时快照的开销，再
   决定要不要按 tile 编码组件分节。
5. **方块游戏的规则接受两项损失**：水源不再两格夹出新水源，挖开的湖会流干，需要无限水源的游戏放
   `WaterSource`；往水里放方块会删掉被占的水（报 `water.displaced`），不会把水推开。
6. **薄水膜可以干掉**：区域新增 `dry_below`，默认 0（不干，水量守恒）；低于它且流速很慢的水膜干掉，
   报 `water.dried`。blockcraft 设 2 mm。
7. **先在 R1 跑 `tools/shallow_check.py`**，与 M5 的哈希链一致后才开始切片 A。
8. **元胞自动机这几个切片里保留**（熔岩与旧场景用它），blockcraft 迁完后再定去留。
9. **`Blocky` 风格**：每个方块上的水面画成平的（取其各列水面的平均），相邻方块之间画竖直的侧面，只改
   绘制。blockcraft 用哪种风格由切片 A 的截图决定。

审阅同时改正了草案的几处错误：开着水花时，只有在水花区域内才不画陡坡，否则 48 m 外的瀑布会消失；区域
由场景或脚本创建，外观取区域自己的 `look`，不读 `field` 液体调色板的 `fog` 与 `splash`；一格液体的水
平均分给该方块上的各列；碰撞体床面要先验证 parry 的射线在各目标上逐位一致；walker 被水推的速度跟随流
速、最高 2 m/s，是有意的改动。

## 5. 架构

### 5.1 crate

2026-10-10，Amoris 采用 Pioneer 的 CPU/runtime 先行成果（源快照
`qiulinfan/amoris-pioneer` 的 `9a3e4b0814959629202629845b85205c42086505`）：

- 原生玩家层由 `amoris-interface` 执行感知、投影、意图与时间控制，`amoris-runtime` 用
  `PlayerSpec` 把声明作为 persisted world state 保存，恢复后重建派生定义。观察者的 team vision
  分享当前可见集，每个 observer 的记忆、事件和测量仍独立；executor 只看该 seat 的感知，
  只写自己的控制 channel。session 的决策点、pacing 和 thinking clocks 不进入世界 hash。
- `Source::Player` 在声明玩家的游戏中只允许 `player.*`，由 runtime、thread、worker 和 host
  一同检查。CLI、MCP 与 HTTP 都可绑定 seat；这是可信本地客户端的角色限制，尚不包含 HTTP
  token grants 或远程身份鉴权。新原生玩家层尚无 LLM course 实测；旧 Python gateway 的模型
  结果不作为原生 seat 层的成绩。规格见 [player.md](spec/player.md)。
- 调试器暂停时的读取来自上一个已发布边界并标明 `paused_at`；step 在断点答复，Stop 可结束
  被断点暂停的 Play；snapshot restore 默认保留 applied scripts，并将 restore/swap 记录进
  replay。构建注入 source-based EngineVersion；Windows host 的启动、compiler 与 check 工具

### 5.2 线程（原生）

- **游戏线程**：在 tick 边界按规范顺序应用命令，运行系统（Rust 与 TS），发布快照与事件。
- **主线程（渲染）**：winit 事件循环；读取最新快照，插值，渲染。
- **服务线程**（tokio）：MCP、编辑器 WebSocket、CDP。
- **资源工作线程**：导入与烘焙。
- 断点暂停只阻塞游戏线程；其余线程照常。

### 5.3 web

- 游戏在 Web Worker 里跑同一个 wasm；页面主线程跑 WebGPU 渲染；快照以 transferable buffer 传递
  （Amoris Pioneer threads spike：10⁵ 实体 0.39 ms）。
