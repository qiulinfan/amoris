Which CLI commands answer while the game is stopped at a script breakpoint
Measured 2026-10-04 by hand (target-debug-eval/release/pocket, main 1e5b94f) on the clean evaluation
game: `pocket debug breakpoints.set '{"file":"scripts/helm.ts","line":54}'`, then `pocket step 1` in
the background (it stops at helm.ts:54 on tick 1), then each command with a 6 s limit.

status                                     blocks (>6 s)
world get Sloop Helm                       blocks (>6 s)
world query Boat --fields Boat.speed       blocks (>6 s)
world tree                                 blocks (>6 s)
scripts list                               blocks (>6 s)
scripts read scripts/main.ts               blocks (>6 s)
events --limit 1                           0.01s answers
logs                                       0.01s answers
snapshots list                             blocks (>6 s)
history                                    blocks (>6 s)
debug state                                0.01s answers
call catalog.list                          blocks (>6 s)
(the background `pocket step 1` itself blocks until `pocket debug continue`: then "tick 1 hash 646aa9a3436c")

docs/spec/debugger.md 8 says "status and snapshots stay readable" while paused, and server.md 2 that
"a game stuck in a tick (a breakpoint) leaves the server answering"; status does not answer, nor do
reads that need no game at all (scripts read, catalog.list). The CLI's HTTP client has a connect
timeout only, so each such call hangs the agent's shell until the agent's tool gives up: opencode's
bash tool killed them after 30 to 120 s in goto-radians/cli-1, anchor-stale/cli-debugger-1,
reach-squared/cli-debugger-1 and others (see docs/bench/debug-eval.md).
