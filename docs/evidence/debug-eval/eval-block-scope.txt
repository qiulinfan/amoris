Cause (third_party/rquickjs-sys-0.14.0/quickjs/quickjs.c, JS_EvalInStackFrame from PR #1421): it
picks the eval's scope as the FIRST local with the deepest scope_level (`if (vd->scope_level >
max_level)`), here `dx`, and add_closure_variables() then walks scope_next from it, which links each
variable to the one declared before it. Variables declared after that one in the same block (`dz`,
`bearing`) are never reached; neither is any block that is not on the deepest block's chain. The
debugger's locals listing (JS_GetLocalVariablesAtLevel) reads every vardef and so shows them.

What it should do: take the scope live at the frame's pc (the innermost block containing the paused
statement) and start from that block's last declared variable. The bytecode keeps no pc-to-scope
map after compilation, so the patch needs one (or the scope's variable range per OP_debug), in the
style of P9's per-function statement table.
