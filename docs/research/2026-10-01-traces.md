# After diagnosing: what agents' traces found, and where to reach next (research, 2026-10-01, late)

Written at 7645ae0, after the benchmark gained a tier of tasks that hand an agent something broken (`docs/agent-eval.md`, Diagnose and fix) and the traces of opencode with GLM 5.3 Flash were read with `tools/scripts/trace_report.py`. What is measured says so; the rest is a plan to be checked the same way.

## What the traces found

Reading an agent's calls in order found faults in the engine that no test had, because no test works the way an agent does: change a file, apply it, look, change again.

- **A reload after a script error kept the old handlers** (fixed in 3f4c16f). On `frozen_coins` the agent fixed the crashing line in its ninth call and spent 35 more learning why `project.apply` still failed: the unload a reload sends was refused while the error stood, so the old tick handler stayed beside the new one and threw again. After the fix the same task took 10 calls and 60 seconds instead of 46 and 660.
- **`script.eval` answered an error with frames only** and could not reach the SDK (fixed in 0947b9f): JavaScriptCore keeps an error's message out of `stack`, and `world` lives inside the bundle.
- **Agents read whole references** (changed in 1160fb2): `docs/generated/sdk.md` (75 KB) and `design/rendering.md` (69 KB) read in one piece, then carried by every later turn. A new project's guide now gives their sizes and says to search them; on the next run both games that had read the SDK reference searched it instead, at well under half the tokens (one run each).
- **A profiler is found when it is named well.** On `slow_swarm` the agent searched the command list for "profil" and used `script.profile` before and after each of its edits; on `festival_flags` it did not need `perf` at all, because the scene file said what was slow.

Where a run's context goes (the forty-eight on opencode, before these changes): each turn starts from about 20,600 tokens (opencode's own prompt, the 31 MCP tools at about 4,000, the task), and files read are most of the rest: 918 KB of reads against 151 KB of engine answers through `runtime_command`.

## Agents, next

1. **Say the likely cause with the error.** A command given `undefined` for an entity answers `missing 'entity'`; from a script that is nearly always a lookup that found nothing or an index past the end (`frozen_coins`'s bug). The SDK knows it was handed `undefined` and can say so, with the call's place. S.
2. **A run of the benchmark against the iOS Simulator.** The harness starts a desktop runtime; one that packs the task's project as an app (`pocket run --ios -- --serve`) would measure whether anything an agent does works the same on the phone target. M.
3. **Mine every run's traces automatically**: the harness could keep `trace_report.py`'s summary beside its report, and flag a task whose calls after the first edit outnumber those before (the shape `frozen_coins` had). S.

## Reach, next

1. **On-screen controls by default** (drafted): a game with keyboard and pad bindings only is unplayable on a phone; at the first touch, a stick for the actions bound to the arrows and a button for each other action, unless the game made its own or turned them off. S.
2. **x86_64 Linux** (running): the archives are pinned but had never run; `POCKET_LINUX_ARCH=amd64 tools/scripts/linux.sh` now builds and tests under Rosetta. Its other use is determinism: whether hello's golden hash, which macOS and Linux on arm64 share, holds on x86_64 too, which lockstep play between such machines needs. S.
3. **An iPhone, not only the simulator**, needs a developer account's signing; the build is the simulator's with another SDK and triple. Blocked on the account.
4. **Android**: SDL3 and wgpu-native support it, but JavaScriptCore is not on Android and would have to be built or replaced (QuickJS, or V8 as ADR 0005 planned for Linux and Windows). L.

## CPU and GPU, measured

- At 1280x720 on an Apple M5 the showcase's GPU frame is 3.66 ms with every effect on (scene 0.80, volumetric fog 0.47, SSR 0.43, TAA 0.41); nothing there stands out.
- In a headless run the tick's `state` phase is often the largest CPU cost (81% of the physics sample's tick): it is the game's own `expose` getters, read every tick, which `script.profile` now times. Engine work there is the JSON of the state and its copies: a few percent.
- A script command's cost is the JSON both ways: a 200-row `world.query` from a script is about 0.5 ms (2.5 µs a row) after the copies were removed. A query that answers columns of numbers through the shared `Float64Array`, as `world.get` does for one entity, would be the next step for games that query every tick. M.
